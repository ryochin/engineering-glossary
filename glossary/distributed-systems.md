# 分散システム

## 結果整合性

別名: Eventual Consistency

### 意味
すべてのレプリカが最終的に同じ状態に収束するが、一時的な不整合が許容される整合性モデル。書き込み直後に別のノードから読み取ると古いデータが返る可能性があるが、時間が経てば全ノードが一致する。

### よくある例
- DynamoDB のデフォルト読み取りは結果整合性。`ConsistentRead: true` を指定しないと、書き込み直後の読み取りで古い値が返ることがある
- ElastiCache（Redis クラスターモード）でレプリカへの読み取りが、プライマリへの書き込みより遅延する
- SQS の標準キューはメッセージの順序と配信が結果整合的。FIFO キューは順序保証付きだがスループットが制限される
- Rails + Sidekiq でジョブ内から DB のリードレプリカを参照すると、直前のトランザクションの変更がまだ反映されていない
- S3 は2020年12月以降、強い整合性（strong consistency）を提供するようになったが、それ以前は結果整合性だった

### ありがちな症状
- 「さっき保存したのにデータが表示されない」というユーザー報告
- リードレプリカを使ったページで、書き込み直後にリダイレクトすると変更が反映されていない
- DynamoDB で `PutItem` 直後の `GetItem` が古い値を返し、フロント側でキャッシュと思い込む
- マイクロサービス間でイベント伝搬の遅延により、一時的にサービス間のデータが矛盾する

### 近い言葉との違い
- 強い整合性（Strong Consistency）: 書き込み完了後は必ず最新値が読める。DynamoDB の `ConsistentRead: true` や RDS のプライマリ読み取り。レイテンシとスループットのトレードオフがある
- [CAP 定理](#cap-定理): 結果整合性は AP（可用性 + 分断耐性）を選択した結果として現れるモデル
- 因果整合性（Causal Consistency）: 因果関係のある操作の順序のみ保証する、結果整合性と強い整合性の中間

### 背景・語源
Werner Vogels（Amazon CTO）が2008年の論文 *Eventually Consistent* で体系的に解説し広めた。Amazon DynamoDB の設計思想の基盤であり、「常に利用可能なシステムを作るには強い整合性を諦める必要がある」という実践的な判断に基づく。概念自体はそれ以前からデータベースの分散レプリケーション研究で存在していた。

### 対策
- 「書き込み後すぐ読む」パターンでは強い整合性読み取りを使う（DynamoDB の `ConsistentRead`、Aurora のライター直接読み取り）
- Rails で `writing_role` / `reading_role` を使い分け、書き込み直後はプライマリから読む
- フロントエンドでは楽観的 UI 更新（Optimistic UI）で、サーバーの反映を待たずにローカルで即時表示する
- イベント駆動アーキテクチャでは、冪等なコンシューマーを実装し、同じイベントが複数回届いても問題ないようにする
- ユーザーに影響する画面では Read-your-writes 保証を意識して設計する

## Split Brain

別名: スプリットブレイン / ネットワーク分断脳

### 意味
クラスタ内でノード間の通信が途絶し、複数のノードが自分をマスター（リーダー）だと認識してしまう状態。両方が書き込みを受け付けるため、データの不整合や競合が発生する。

### よくある例
- Redis Sentinel 構成でネットワーク分断が発生し、旧マスターと新マスター（Sentinel によって昇格）が同時に書き込みを受け付ける。分断解消後に旧マスターのデータが失われる
- Elasticsearch クラスタで `minimum_master_nodes` の設定が不適切な場合、ネットワーク分断時に複数のマスターノードが選出される
- Kafka のコントローラーブローカーが ZooKeeper との接続を失い、新コントローラーが選出されるが、旧コントローラーがまだ動作し続ける
- ECS + RDS Multi-AZ で AZ 間のネットワークが不安定になり、フェイルオーバーが中途半端な状態で止まる
- Kubernetes の etcd クラスタでノード間の通信が途絶し、2つの独立したクラスタとして動作し始める

### ありがちな症状
- 同じキーに対して異なる値が存在する（データの分岐）
- フェイルオーバー後にデータが巻き戻る、または一部が消失する
- 「書き込んだはずのデータがない」という報告
- クラスタのノード数が奇数でなく、過半数の合意が取れないまま複数グループが独立動作する

### 近い言葉との違い
- [CAP 定理](#cap-定理): Split Brain は CAP 定理の P（ネットワーク分断）が実際に起きたときの具体的な症状
- [結果整合性](#結果整合性): 結果整合性は設計上の許容。Split Brain は意図しない障害による不整合
- フェイルオーバー: Split Brain はフェイルオーバーの失敗パターンの一つ

### 背景・語源
脳科学の分離脳（split-brain）から借用した用語。脳梁を切断された患者の左右の脳半球が独立して動く現象に由来する。Roger Sperry が1960年代に分離脳の研究でノーベル生理学・医学賞（1981年）を受賞した。分散システムでは、ネットワーク分断によってクラスタが互いに通信できない2つのグループに分かれ、それぞれが独立して動作する様子がこの現象に似ていることから名付けられた。

### 対策
- クラスタのノード数を奇数（3, 5, 7）にし、過半数（quorum）による合意を必須にする
- Redis Sentinel では `min-replicas-to-write` と `min-replicas-max-lag` を設定し、レプリカと通信できないマスターが書き込みを拒否するようにする
- Elasticsearch では `discovery.zen.minimum_master_nodes` を `(ノード数 / 2) + 1` に設定する（7.x 以降はデフォルトで適切に設定される）
- Kubernetes の etcd は3台以上の奇数台で構成し、`--election-timeout` と `--heartbeat-interval` を適切に設定する
- フェンシング（fencing）: 旧マスターが書き込みを続けないよう、STONITH（Shoot The Other Node In The Head）で強制的に旧ノードを停止させる

## CAP 定理

別名: CAP Theorem / ブリューワーの定理

### 意味
分散システムは Consistency（一貫性）、Availability（可用性）、Partition tolerance（分断耐性）の3つの性質を同時に満たすことができないという定理。ネットワーク分断は避けられないため、実際には CP（一貫性 + 分断耐性）か AP（可用性 + 分断耐性）の選択になる。

### よくある例
- DynamoDB はデフォルトで AP を選択（結果整合性 + 高可用性）。`ConsistentRead: true` を指定すると CP 寄りになる
- Redis Sentinel / Cluster は AP 寄り。マスターフェイルオーバー時に書き込みが失われる可能性がある
- PostgreSQL（RDS Multi-AZ）は CP 寄り。同期レプリケーションで一貫性を保証するが、フェイルオーバー中は一時的に利用不可になる
- ZooKeeper / etcd は CP。過半数のノードが応答しないとクラスタ全体が書き込みを拒否する
- Cassandra は AP がデフォルトだが、一貫性レベル（`QUORUM`、`ALL`）を調整して CP 寄りにできる

### ありがちな症状
- 「2つ選べ」を文字通り受け取り、「うちは CA だからネットワーク分断は起きない」と誤認する
- 分散 DB の選定時に CAP だけで判断し、レイテンシやスループットのトレードオフを見落とす
- マネージドサービスの設定（DynamoDB の整合性レベル、Redis のレプリケーション設定）を深く理解せず使っている

### 近い言葉との違い
- [結果整合性](#結果整合性): AP を選択した場合の具体的な整合性モデル
- [Split Brain](#split-brain): P（ネットワーク分断）が実際に起きたときの障害パターン
- PACELC 定理: CAP をより実用的に拡張した定理。分断がない通常時にも Latency と Consistency のトレードオフがあることを示す（Daniel Abadi、2012年）
- BASE（Basically Available, Soft state, Eventually consistent）: AP システムの設計原則を ACID に対比させた頭字語

### 背景・語源
Eric Brewer が2000年の ACM PODC（Principles of Distributed Computing）シンポジウムで推測（conjecture）として発表した。2002年に Seth Gilbert と Nancy Lynch が MIT で形式的に証明し、定理となった。「2つ選べ」という表現は直感的だが過度な単純化であり、実際にはネットワーク分断は必ず起きるため CA の選択肢は存在しない。2012年に Daniel Abadi が提唱した PACELC 定理は、通常時（Else）の Latency vs Consistency のトレードオフも含めたより実用的な枠組みを提供する。

### 対策
- 分散 DB やメッセージブローカーの選定時に、自システムが CP と AP のどちらを重視するか明確にする
- DynamoDB では読み取りの整合性レベルをユースケースに応じて使い分ける（参照系は結果整合性、クリティカルな読み取りは強い整合性）
- Redis を使う場合、フェイルオーバー時のデータ損失許容度を事前に合意する
- CAP だけでなく、レイテンシ・スループット・運用コスト・エコシステムも含めた総合判断で技術選定する
- Terraform で Multi-AZ / Multi-Region 構成を組む場合、リージョン間のレプリケーション遅延を見積もる

## Two Generals Problem

別名: 二人の将軍問題 / 二将軍問題

### 意味
2つの軍隊が敵を挟んで協調攻撃する必要があるが、連絡に使うメッセンジャーが途中で敵に捕まる可能性がある場合、「攻撃の合意」に確実に至ることが理論的に不可能であるという問題。分散システムにおける信頼性のないネットワーク上でのメッセージ配信の根本的な限界を示す。

### よくある例
- マイクロサービス間の API 呼び出しで、レスポンスがタイムアウトした場合、相手が処理を完了したのかしていないのか判断できない
- 決済 API（Stripe、PayPay）にリクエストを送ったが、タイムアウトで応答がない。課金されたのかされていないのか不明
- SQS にメッセージを送信した直後にプロセスがクラッシュし、メッセージが届いたか確認できない
- Kafka のプロデューサーが `acks=all` でメッセージを送信してもブローカーの応答を受け取る前にクラッシュすると、メッセージが永続化されたか不明
- ECS のタスク間で gRPC 通信を行う際、ネットワーク断で応答がない場合の扱い

### ありがちな症状
- API 呼び出しのタイムアウト後に「もう一度呼ぶべきか」で悩む
- 「このメッセージは届いたのか？」が確認できない
- 重複リクエストを恐れてリトライしない、または考えなしにリトライして二重処理が発生する
- 分散トランザクションの「最後の1ステップ」で不整合が生まれる

### 近い言葉との違い
- ビザンチン将軍問題: ノードが悪意を持って嘘をつく可能性がある場合の合意問題。Two Generals Problem はノードは誠実だがメッセージが失われるケース
- [CAP 定理](#cap-定理): CAP はシステム全体の設計選択。Two Generals Problem は個々のメッセージ交換レベルの不可能性
- [Idempotency Key](#idempotency-key): Two Generals Problem への実用的な対策の一つ

### 背景・語源
1975年に Jim Gray が定式化した。1982年に Akkoyunlu、Ekanadham、Huber が「信頼性のない通信路での合意は不可能である」ことを形式的に証明した。TCP の3ウェイハンドシェイク（SYN → SYN-ACK → ACK）はこの問題の実用的な「十分な」解決策であり、理論的な完全解ではないが、現実のネットワークでは実用上十分に機能する。

### 対策
- リクエストに [Idempotency Key](#idempotency-key) を付与し、安全にリトライできるようにする
- タイムアウト時は「相手がどちらの状態か」を照会する API を用意する（Stripe の `PaymentIntent` ステータス確認など）
- at-least-once 配信 + 冪等な受信側の組み合わせで、重複を許容しつつ結果の正しさを保証する
- Kafka では `enable.idempotence=true` でプロデューサーの冪等性を有効にする
- SQS + Lambda では `messageDeduplicationId` や受信側の冪等性チェックで二重処理を防ぐ

## Saga パターン

別名: Saga Pattern / サーガパターン

### 意味
マイクロサービス間の分散トランザクションを、一連のローカルトランザクションとそれぞれに対応する補償トランザクション（compensating transaction）で管理するパターン。各ステップが成功すれば次に進み、失敗したら補償トランザクションで前のステップを巻き戻す。

### よくある例
- EC サイトの注文処理: 在庫確保 → 決済 → 配送手配。決済が失敗したら在庫確保を取り消す補償トランザクションを実行する
- Rails のマイクロサービス構成で、ユーザー登録サービス → メール配信サービス → ポイント付与サービスを順に呼び出す。ポイント付与が失敗したらメール取り消し → ユーザー仮登録状態に戻す
- AWS Step Functions で Saga パターンを実装し、各ステップの Lambda に対応するロールバック用 Lambda を定義する
- Kafka を使った Choreography 型 Saga: 各サービスがイベントを消費して処理し、次のイベントを発行する。失敗時は補償イベントを発行する

### ありがちな症状
- マイクロサービス間で分散トランザクションが必要なのに、2フェーズコミット（2PC）を使おうとしてパフォーマンスが劣化する
- 途中のステップが失敗したときのロールバックが手動対応になっている
- 補償トランザクションの設計が漏れており、中途半端な状態のデータが残る
- 「注文は作成されたが決済されていない」「在庫は引かれたが注文がない」といった不整合データ

### 近い言葉との違い
- 2フェーズコミット（2PC）: 全ノードで同時にコミットまたはロールバックする強い一貫性の仕組み。Saga はローカルトランザクションの連鎖で結果整合性を実現する
- [結果整合性](#結果整合性): Saga パターンは結果整合性を前提とした分散トランザクションの実装手段
- [Idempotency Key](#idempotency-key): Saga の各ステップを安全にリトライするための実装手段
- Choreography vs Orchestration: Choreography はイベント駆動で各サービスが自律的に動く方式。Orchestration は中央のコーディネーター（Step Functions など）が各ステップを制御する方式

### 背景・語源
Hector Garcia-Molina と Kenneth Salem が1987年の論文 *Sagas* で提唱した。元々は単一データベースにおける長時間トランザクション（Long Lived Transaction、LLT）の問題を解決するために考案された。LLT はロックを長時間保持するため並行性が低下する問題があり、それを短いトランザクションの連鎖に分解する手法として Saga が生まれた。マイクロサービスアーキテクチャの普及に伴い、サービス間の分散トランザクション管理手法として再注目された。

### 対策
- 小規模なシステムや明確なフローには Orchestration 型（AWS Step Functions、Temporal）を選ぶ
- サービス間の結合を緩くしたい場合は Choreography 型（Kafka、SQS + SNS）を選ぶ
- 各ステップに補償トランザクションを必ず設計し、ドキュメント化する
- 各ステップを冪等に実装し、リトライ時に二重実行されても問題ないようにする
- Saga の状態をログに記録し、途中で止まった Saga を検出して修復できる仕組みを入れる（Saga ログ）
- Terraform + Step Functions で Saga のワークフローを IaC 管理し、環境間の差異をなくす

## Idempotency Key

別名: 冪等キー / べき等キー / リクエスト識別キー

### 意味
API リクエストに一意のキー（UUID など）を付与し、同じキーのリクエストが複数回送信されても1回だけ処理されるようにする実装パターン。ネットワーク障害やタイムアウトで応答が不明な場合に、安全にリトライできるようにする。

### よくある例
- Stripe API の `Idempotency-Key` ヘッダー: 同じキーで決済リクエストを再送しても、2回目以降はキャッシュされた結果を返す
- SQS FIFO キューの `MessageDeduplicationId`: 同じ ID のメッセージは5分間の重複排除ウィンドウ内で1回だけ配信される
- Rails の API で `X-Idempotency-Key` ヘッダーを受け取り、Redis にキーと処理結果を保存する。同じキーの再リクエストには保存済みの結果を返す
- DynamoDB の `ConditionExpression` で `attribute_not_exists(idempotency_key)` を指定し、同じキーの書き込みを拒否する
- Kafka のプロデューサーで `enable.idempotence=true` を設定すると、ブローカーがシーケンス番号で重複メッセージを検出・排除する

### ありがちな症状
- API のタイムアウト後にリトライしたら二重課金が発生した
- 同じ注文が2つ作成された
- ネットワーク障害後の「もう一度試してください」で副作用が二重に実行される
- フロントエンドの「送信」ボタンのダブルクリックで重複リクエストが飛ぶ
- Sidekiq のリトライで同じジョブが複数回実行され、メール通知が重複送信される

### 近い言葉との違い
- 冪等性（Idempotency）: 「同じ操作を何度実行しても結果が変わらない」という設計原則。Idempotency Key はその実装手段の一つ
- HTTP メソッドの冪等性: GET, PUT, DELETE は仕様上冪等。POST は非冪等。Idempotency Key は非冪等な POST を実質的に冪等にする仕組み
- [Two Generals Problem](#two-generals-problem): Idempotency Key は Two Generals Problem に対する実用的な対策
- 重複排除（Deduplication）: メッセージレベルの重複排除（SQS FIFO の `MessageDeduplicationId`）は Idempotency Key と同じ発想

### 対策
- 決済、注文、ポイント付与など副作用のある API には必ず Idempotency Key を実装する
- キーの保存先は Redis（TTL 付き）や DynamoDB が一般的。キーと処理結果（ステータスコード + レスポンスボディ）をセットで保存する
- キーの有効期間（TTL）を設定し、ストレージが無限に膨らまないようにする（Stripe は24時間）
- クライアント側でリクエストごとに UUID v4 を生成し、リトライ時は同じキーを再送する
- フロントエンドでは送信ボタンの二重クリック防止（disable）と併用する。Idempotency Key はサーバー側の最後の砦
- SQS + Lambda の構成では `messageDeduplicationId` と受信側の冪等性チェックを組み合わせ、二重処理を防ぐ
