## TOCTOU

別名: Time-of-check to time-of-use / 検査時と使用時の競合

### 意味
「チェックした時点」と「実際に使う時点」の間に状態が変わってしまうバグ。チェック結果が使用時には既に無効になっている。

### よくある例
- ファイルの存在を `File.exist?` で確認してから `File.open` するまでに、別プロセスがファイルを削除する
- Terraform で `plan` 時に確認したリソース状態が、`apply` 時には別の人の変更で変わっている
- Rails で `unless User.exists?(email:)` → `User.create!(email:)` の間に別リクエストが同じメールで作成し、一意制約違反になる

### ありがちな症状
- 「テストでは通るのに本番でたまに失敗する」
- if 文で存在チェックしてから操作しているコードが散見される
- 同時アクセスが増えた途端にエラー率が上がる

### 近い言葉との違い
- [レースコンディション](#レースコンディション): TOCTOU はレースコンディションの一種。チェックと使用が分離している特定パターン
- [アトミック操作](#アトミック操作): TOCTOU の根本対策。チェックと操作を分割不可能にする
- [チェック・アンド・セット](#チェックアンドセット): TOCTOU を防ぐための具体的テクニック

### 背景・語源
Time of Check to Time of Use の略。セキュリティ分野で1990年代から知られる脆弱性のクラス。Matt Bishop と Michael Dilger が1996年の論文で形式的に分析した。ファイルシステムのレースコンディションを悪用する攻撃手法として、UNIX セキュリティの文脈で特に重要視されてきた。

### 対策
- DB のユニーク制約やアドバイザリーロックで「チェックと操作」を一体化する
- `INSERT ... ON CONFLICT` や `find_or_create_by` + リトライのようなアトミック操作を使う
- ファイル操作では `O_CREAT | O_EXCL` フラグで「存在しなければ作成」をアトミックに行う
- Terraform では state lock を有効にし、CI で plan と apply を同一パイプラインで実行する

## レースコンディション

別名: Race Condition / 競合状態

### 意味
複数のプロセスやスレッドが共有リソースに同時アクセスし、実行順序によって結果が変わってしまう状態。タイミング依存のバグの総称。

### よくある例
- Rails の Sidekiq ワーカーが同じレコードを同時に更新し、片方の変更が消える（lost update）
- CI の並列ジョブが同じ S3 バケットのファイルを同時に書き換え、内容が壊れる
- Docker Compose で依存サービスの起動順が保証されず、接続エラーになる
- ECS タスクが複数同時にデプロイされ、DB マイグレーションが重複実行される

### ありがちな症状
- 「10回中1回だけ失敗する」「再現性がない」
- テストが CI 上でだけランダムに落ちる（フレーキーテスト）
- 負荷テストで初めて発覚する不整合

### 近い言葉との違い
- [TOCTOU](#toctou): レースコンディションの特定パターン（チェック→使用の間のギャップ）
- [デッドロック](#デッドロック): 競合の結果「止まる」のがデッドロック、「壊れる」のがレースコンディション
- [フレーキーテスト](testing.md#フレーキーテスト): レースコンディションが原因でテストが不安定になった結果

### 対策
- 共有リソースへのアクセスにはロック（mutex, DB ロック, アドバイザリーロック）を使う
- 冪等な設計にし、重複実行されても同じ結果になるようにする
- Rails では `with_lock` や `lock!`、DB レベルの `SELECT ... FOR UPDATE` を活用する
- CI/CD では DB マイグレーションを単一ジョブに限定し、ロック機構を入れる

### 関連用語

## アトミック操作

別名: Atomic Operation / 不可分操作

### 意味
途中で中断されたり、他の操作が割り込んだりすることがない、分割不可能な操作。「全部成功するか、何も起きないか」の二択になる。

### よくある例
- DB の `INSERT ... ON CONFLICT DO UPDATE` は「存在確認と挿入/更新」をアトミックに行う
- Redis の `INCR` はカウンタの読み取りと加算を一度に行うアトミック操作
- Terraform の state lock は plan〜apply の間に他の操作を割り込ませないための仕組み
- Linux の `rename(2)` はファイルの移動をアトミックに行う（中間状態が見えない）

### ありがちな症状
- 「SELECT してから UPDATE する」コードでデータ不整合が起きる
- カウンタが実際より少ない値になる（lost update）
- 部分的に更新された中間状態のデータが見える

### 近い言葉との違い
- トランザクション: トランザクションは複数操作をまとめてアトミックにする仕組み。アトミック操作は単一操作レベル
- [チェック・アンド・セット](#チェックアンドセット): CAS はアトミック操作の代表的な実装パターン
- [Optimistic Locking](#optimistic-locking--pessimistic-locking): 楽観ロックはアトミックな比較+更新を利用する

### 対策
- 「読み取り→判断→書き込み」を分けず、DB やミドルウェアが提供するアトミック命令を使う
- Redis なら `INCR`, `SETNX`, Lua スクリプト。PostgreSQL なら `INSERT ... ON CONFLICT`
- ファイル更新は「一時ファイルに書いてから rename」パターンで原子的に切り替える
- アプリケーション層でアトミック性を実現しようとせず、下位レイヤーに任せる

### 関連用語

- [チェック・アンド・セット](#チェックアンドセット)
- [レースコンディション](#レースコンディション)

## チェック・アンド・セット

別名: CAS / Compare-and-Swap / 比較交換

### 意味
「現在の値が期待値と一致していたら新しい値に更新する」というアトミック操作。値が変わっていたら更新を拒否し、呼び出し元にリトライさせる。

### よくある例
- DynamoDB の `ConditionExpression` で「version = :expected」を指定して更新する
- Redis の `WATCH` + `MULTI` / `EXEC` パイプラインで楽観ロックを実現する
- Rails の `lock_version` カラムによる Optimistic Locking（内部的に CAS）
- etcd / Consul の KV ストアで `ModifyIndex` を使った条件付き書き込み

### ありがちな症状
- 楽観ロックの失敗（`StaleObjectError` など）が頻発する場合、競合が激しすぎるサイン
- リトライループが終わらない（競合頻度が高すぎて CAS が何度も失敗する）

### 近い言葉との違い
- [アトミック操作](#アトミック操作): CAS はアトミック操作の一種
- [Optimistic Locking](#optimistic-locking--pessimistic-locking): 楽観ロックは CAS の応用。CAS はより低レベルの概念
- [ABA問題](#aba問題): CAS の弱点。値が A→B→A と変わると、CAS は変化を検出できない

### 対策
- 競合が少ない場合は CAS + リトライで十分
- 競合が多い場合は Pessimistic Locking への切り替えを検討する
- リトライには exponential backoff を入れ、無限ループを防ぐ
- ABA問題を避けるために、単純な値ではなくバージョン番号やタイムスタンプを比較対象にする

## デッドロック

別名: Deadlock / 相互排他待ち

### 意味
複数のプロセスやスレッドが互いにロックの解放を待ち合い、全員が永久に停止する状態。誰も先に進めない。

### よくある例
- PostgreSQL でトランザクション A がテーブル X → Y の順にロック、トランザクション B が Y → X の順にロックし、互いに待ち合う
- Rails で `with_lock` をネストして使い、異なる順序でレコードをロックしてしまう
- Terraform の state lock が残ったまま次の CI ジョブが走り、`force-unlock` しないと進めない（厳密にはデッドロックではないが症状が似ている）
- Docker コンテナ内のプロセスがファイルロックを取得したまま異常終了し、再起動後にロックファイルが残る

### ありがちな症状
- プロセスやクエリが「何もせずハングする」
- PostgreSQL の `pg_stat_activity` に `waiting` 状態のクエリが複数ある
- `deadlock detected` のエラーログが出る（PostgreSQL は自動検出して片方をキャンセルする）
- 特定の処理だけタイムアウトする

### 近い言葉との違い
- [ライブロック](#ライブロック): デッドロックは「止まる」、ライブロックは「動いてるけど進まない」
- [スターベーション](#スターベーション): デッドロックは全員止まる、スターベーションは特定のプロセスだけ永遠に後回しにされる
- [レースコンディション](#レースコンディション): レースコンディションはデータが壊れる、デッドロックは処理が止まる

### 背景・語源
E.G. Coffman, Jr. らが1971年の論文で、デッドロックの発生条件を4つ（相互排他、保持と待機、横取り不可、循環待ち）に整理した（Coffman conditions）。概念自体はそれ以前からOS設計で知られていたが、この4条件の定式化が教科書的な標準となった。

### 対策
- ロックの取得順序をシステム全体で統一する（例: テーブル名のアルファベット順）
- ロックにタイムアウトを設定する（`SET lock_timeout = '5s'`）
- デッドロック検出機能のある DB を使い、自動的に片方をロールバックさせる
- 可能なら楽観ロックに切り替えてロック自体を避ける
- ロックファイルを使う場合は PID を記録し、起動時に stale lock を検出・削除する

## ライブロック

別名: Livelock

### 意味
プロセスやスレッドが互いに譲り合い続け、どちらも実行中（CPU を消費している）だが実質的に先に進めない状態。デッドロックと違い「動いている」のが厄介。

### よくある例
- 2つのワーカーが同じリソースのロック取得に失敗→即リトライ→また衝突を永遠に繰り返す
- メッセージキューで処理失敗→リトライ→また失敗を高速で繰り返し、キューが詰まる（poison message）
- Kubernetes の Pod が CrashLoopBackOff で再起動を繰り返すが、依存サービスが落ちているため毎回同じ理由で失敗する
- 2つのサービスが互いに「相手の準備ができてから起動する」設定になっていて、両方ともヘルスチェック待ちで止まる

### ありがちな症状
- CPU 使用率は高いのにスループットがゼロ
- ログにリトライのメッセージが大量に流れ続ける
- プロセスは生きているのに処理が全く進まない

### 近い言葉との違い
- [デッドロック](#デッドロック): デッドロックは止まる、ライブロックは動いてるけど進まない
- [スターベーション](#スターベーション): ライブロックは全員進まない、スターベーションは特定のプロセスだけ飢餓状態
- [リトライストーム](operations.md#リトライストーム): ライブロックの一因になりうる。多数のクライアントが同時リトライする

### 対策
- リトライにランダムな jitter（ゆらぎ）を入れ、衝突タイミングをずらす
- exponential backoff を導入し、リトライ間隔を徐々に広げる
- リトライ上限を設け、超えたらデッドレターキューに送る
- 依存関係のある起動順序は Docker Compose の `healthcheck` + `depends_on.condition` や init コンテナで制御する

## スターベーション

別名: Starvation / 飢餓状態 / リソース飢餓

### 意味
特定のプロセスやスレッドが、他の優先度の高い処理にリソースを奪われ続け、いつまでも実行されない状態。システム全体は動いているが、一部だけが永遠に待たされる。

### よくある例
- PostgreSQL で長時間トランザクションがロックを保持し続け、後続のクエリがタイムアウトする
- Sidekiq で優先度の高いキューのジョブが大量に来ると、低優先度キューのジョブが何時間も処理されない
- Kubernetes で CPU/メモリの requests を設定していない Pod が、他の Pod にリソースを奪われて OOMKill される
- CI の共有ランナーが大きなプロジェクトに占有され、小さなプロジェクトの CI がキュー待ちのまま

### ありがちな症状
- 特定のジョブやリクエストだけが異常に遅い
- 「他は動いてるのにこれだけ進まない」
- 低優先度のタスクの SLA が守れない

### 近い言葉との違い
- [デッドロック](#デッドロック): 全員止まるのがデッドロック、一部だけ止まるのがスターベーション
- [ライブロック](#ライブロック): 全員動いてるけど進まないのがライブロック
- [Priority Inversion](#priority-inversion優先度逆転): 優先度逆転はスターベーションの原因の一つ。高優先度タスクが低優先度タスクに間接的にブロックされる

### 対策
- フェアネスを保証するスケジューリング（ラウンドロビン、weighted fair queuing）を使う
- Sidekiq の場合、キューごとにプロセスを分離するか weight を設定する
- Kubernetes では resource requests/limits を適切に設定し、QoS クラスを管理する
- DB の長時間トランザクションには `statement_timeout` や `idle_in_transaction_session_timeout` を設定する

## ABA問題

別名: ABA Problem

### 意味
CAS（Compare-and-Swap）で値を比較する際、値が A→B→A と変遷していた場合に「変化していない」と誤判定してしまう問題。値だけを見ると元に戻っているが、間に別の状態を経由している。

### よくある例
- ロックフリーのスタックで、ノード A をポップした後に別スレッドが A を再利用して push し直すと、CAS が成功してしまいデータ構造が壊れる
- DB で在庫数が `10 → 0 → 10` と変わった場合、「在庫が10なら処理する」という CAS 条件がすり抜ける（実際は一度売り切れている）
- Redis で `WATCH` しているキーの値が変更後に元の値に戻ると、トランザクションが想定外に成功する

### ありがちな症状
- CAS ベースの楽観ロックを使っているのに、稀にデータ不整合が起きる
- 「値は同じだが状態は違う」ケースで整合性が崩れる
- ロックフリーデータ構造で説明のつかないクラッシュが起きる

### 近い言葉との違い
- [チェック・アンド・セット](#チェックアンドセット): CAS 自体は正しいが、ABA問題は CAS の盲点
- [レースコンディション](#レースコンディション): ABA問題はレースコンディションの特殊なケース
- [TOCTOU](#toctou): TOCTOU は「チェックと使用の間の変化」全般、ABA は「値が戻る」特定パターン

### 背景・語源
Compare-and-Swap（CAS）操作に関連する並行処理の問題。値が A → B → A と変化した場合、CAS は「変化していない」と誤判定する。ロックフリーデータ構造の研究で1980年代から知られており、名前は値の遷移パターン（A-B-A）そのままに由来する。

### 対策
- 値そのものではなく、単調増加するバージョン番号やタイムスタンプを比較対象にする
- Rails の `lock_version` カラムは値が戻らない（常にインクリメント）ので ABA 安全
- DynamoDB では `version` 属性を ConditionExpression に使い、値ではなく更新回数で判定する
- ロックフリーデータ構造ではタグ付きポインタ（ポインタ + カウンタ）を使う

## Thundering Herd（サンダリングハード）

別名: Thundering Herd Problem / 殺到問題

### 意味
待機していた大量のプロセスやリクエストが同時に動き出し、システムに一気に負荷がかかる問題。キャッシュの有効期限切れやサービスの復旧時に発生しやすい。

### よくある例
- Redis のキャッシュが expire した瞬間に、数百リクエストが同時に DB へ問い合わせる（cache stampede）
- ECS のデプロイでコンテナが一斉に起動し、DB コネクションプールが枯渇する
- 障害復旧後、溜まっていたリトライが一斉に発火し、復旧したばかりのサービスが再度ダウンする
- cron ジョブが全サーバーで同時刻に実行され、外部 API にリクエストが殺到する

### ありがちな症状
- キャッシュ expire 直後にレスポンスタイムが急激に悪化する
- サービス復旧の直後に再度障害が発生する
- DB のコネクション数やクエリ数が瞬間的にスパイクする
- 特定時刻（毎時0分など）にだけ負荷が集中する

### 近い言葉との違い
- [リトライストーム](operations.md#リトライストーム): リトライ起因の殺到。Thundering Herd の一因
- [レースコンディション](#レースコンディション): Thundering Herd はレースコンディションを伴うことが多いが、本質は「同時殺到」
- [バックプレッシャー](operations.md#バックプレッシャー): Thundering Herd への対策の一つ

### 背景・語源
UNIX/Linux のネットワークプログラミングで古くから知られる問題。`accept()` を待つ複数のプロセスが一斉に起きる現象から「雷鳴に驚いて群れが一斉に走り出す」牛の暴走（stampede）に例えた。Linux カーネルでは `accept()` の thundering herd 問題は解消されたが、アプリケーションレベルでは依然としてキャッシュの一斉失効などで発生する。

### 対策
- キャッシュの expire に jitter（ランダムなばらつき）を加え、同時失効を避ける
- cache lock（最初の1リクエストだけ DB に問い合わせ、他は待機）を実装する
- cron ジョブの実行時刻をサーバーごとにずらす（`sleep $((RANDOM % 60))` など）
- サービス復旧時はトラフィックを段階的に戻す（Canary Deploy 的なアプローチ）
- ECS のデプロイは `minimumHealthyPercent` と `maximumPercent` でローリング更新にする

## Priority Inversion（優先度逆転）

別名: Priority Inversion / 優先度の逆転

### 意味
低優先度のタスクがロックを保持している間に、高優先度のタスクがそのロックを待たされ、結果として中優先度のタスクが先に実行されてしまう現象。優先度の設計が逆転する。

### よくある例
- リアルタイム処理（高優先度）が DB のロックを待っている間に、バッチ処理（中優先度）が CPU を使い、ロック保持中の低優先度タスクが実行されない
- Kubernetes で高優先度の Pod が低優先度の Pod が保持する PersistentVolume の解放を待つ間、中優先度の Pod がノードリソースを消費する
- systemd で高優先度のサービスが低優先度サービスのソケットアクティベーション完了を待ち、起動が遅延する
- CI で緊急のホットフィックスパイプラインが、共有リソース（テスト DB など）をバッチテストに占有され、通常のデプロイパイプラインに追い越される

### ありがちな症状
- 高優先度の処理なのに、中優先度の処理より遅い
- 「優先度を上げたのに改善しない」
- リアルタイム性が求められる処理のレイテンシが不安定

### 近い言葉との違い
- [スターベーション](#スターベーション): 優先度逆転はスターベーションの原因の一つ。スターベーションはより一般的な「飢餓」
- [デッドロック](#デッドロック): デッドロックは互いに待ち合って止まる。優先度逆転は止まらないが遅延する
- [ライブロック](#ライブロック): 全員進まないのがライブロック。優先度逆転は特定の高優先度タスクだけが遅延する

### 背景・語源
1997年の NASA Mars Pathfinder ミッションで発生した事例が有名。火星探査機 Sojourner のリアルタイム OS（VxWorks）で、低優先度タスクがロックを保持し、高優先度タスクがブロックされる優先度逆転が発生してシステムがリセットを繰り返した。地上からのパッチで priority inheritance プロトコルを有効にして解決した。

### 対策
- Priority Inheritance（優先度継承）: ロックを保持している低優先度タスクの優先度を一時的に引き上げる
- Priority Ceiling（優先度上限）: ロックに優先度上限を設定し、ロック取得時にその優先度まで引き上げる
- 共有リソースのロック保持時間を最小限にする
- CI では共有リソースごとに専用ランナーを割り当てるか、リソースプーリングを導入する
- 可能であればロック不要な設計（メッセージパッシング、イベント駆動）に変更する

## Optimistic Locking / Pessimistic Locking

別名: 楽観ロック / 悲観ロック / 楽観的排他制御 / 悲観的排他制御

### 意味
**楽観ロック**: 競合は稀だと仮定し、更新時にバージョン番号などで競合を検出する方式。競合時はエラーにしてリトライさせる。
**悲観ロック**: 競合が起きると仮定し、読み取り時点からロックを取得して他のアクセスをブロックする方式。

### よくある例

悪い例（ロックなし）:
- 2人が同時に管理画面で同じレコードを編集し、後から保存した方の変更だけが残る（lost update）

良い例（楽観ロック）:
- Rails の `lock_version` カラム。更新時に `WHERE lock_version = ?` で競合を検出し、`ActiveRecord::StaleObjectError` を発生させる
- DynamoDB の `ConditionExpression` でバージョン番号を条件にした条件付き書き込み
- Terraform の state file に含まれる serial 番号

良い例（悲観ロック）:
- Rails の `with_lock` / `lock!` で `SELECT ... FOR UPDATE` を発行し、トランザクション終了まで他をブロックする
- 決済処理など「絶対に競合させたくない」場面での排他制御

### ありがちな症状
- 楽観ロック: `StaleObjectError` や `ConditionalCheckFailedException` が頻発する → 競合が多すぎるサイン
- 悲観ロック: クエリのレスポンスタイムが悪化し、`lock_timeout` エラーが出る → ロック保持時間が長すぎる
- どちらも使っていない: 同時更新でデータが消える（lost update）

### 近い言葉との違い
- [チェック・アンド・セット](#チェックアンドセット): 楽観ロックの実装に CAS を使う。CAS はより低レベルの概念
- [アトミック操作](#アトミック操作): ロックはアトミック性を保証する手段の一つ
- [デッドロック](#デッドロック): 悲観ロックを多用するとデッドロックのリスクが上がる
- [ABA問題](#aba問題): 楽観ロックでバージョン番号を使えば ABA 安全。値だけの比較は ABA に弱い

### 対策
- 競合が少ない（読み取り多・書き込み少）なら楽観ロックを選ぶ
- 競合が多い、または絶対に失敗させたくない処理は悲観ロックを選ぶ
- 楽観ロックの失敗時はユーザーに「他の人が更新しました、再読込してください」と通知する
- 悲観ロックのタイムアウトを必ず設定し、デッドロックを防ぐ
- Rails では管理画面のフォームに `lock_version` を hidden field で埋め込むのが定番
