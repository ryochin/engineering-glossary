## SPOF

別名: Single Point of Failure / 単一障害点

### 意味
そこが壊れるとシステム全体が止まる、たった一つの箇所。冗長化されていないコンポーネントがこれに該当する。

### よくある例
- RDS を Single-AZ で運用しており、AZ 障害でサービス全停止
- Nginx が1台しかなく、そのインスタンスの障害で全トラフィックが遮断される
- 特定のエンジニア1人だけがデプロイ手順を知っている（人的 SPOF）

### ありがちな症状
- 「あのサーバーが落ちたら終わり」という暗黙の前提がある
- 障害時にフェイルオーバーが存在しない
- 構成図を書いたとき、ある1箇所を通らないと何もできない

### 近い言葉との違い
- [バルクヘッド](#バルクヘッド): SPOF を解消するための隔離パターン
- [グレースフルデグラデーション](#グレースフルデグラデーション): SPOF が壊れても全体を止めない設計思想
- [ヘルスチェック](#ヘルスチェック): SPOF の障害を検知する手段

### 対策
- AWS なら Multi-AZ 構成を基本にする（RDS Multi-AZ、ALB + 複数 AZ の ECS タスク）
- ロードバランサーの背後に複数台のインスタンスを配置する
- DNS レベルの冗長化（Route 53 のフェイルオーバールーティング）
- 人的 SPOF は Runbook の整備とクロストレーニングで解消する

## サーキットブレーカー

別名: Circuit Breaker

### 意味
依存先のサービスが応答しないとき、一定回数の失敗を検知したら呼び出し自体を止める仕組み。電気回路のブレーカーと同じ発想で、障害の連鎖を遮断する。

### よくある例
- マイクロサービスで外部 API が遅延しているとき、タイムアウト待ちのスレッドが溜まってアプリ全体がハングする前にブレーカーを落とす
- Rails アプリから決済 API を呼ぶ際、3回連続失敗したら一定時間リクエストをスキップしフォールバック応答を返す
- ECS 上のサービス間通信で、App Mesh や Envoy のサーキットブレーカー設定で自動遮断する

### ありがちな症状
- 依存先が遅いだけで自分のサービスまで巻き込まれて応答不能になる
- エラーログが同じ外部サービスへのタイムアウトで埋め尽くされる
- 1つの下流障害がカスケード障害に発展する

### 近い言葉との違い
- [リトライストーム](#リトライストーム): サーキットブレーカーが無いままリトライすると発生する
- [バルクヘッド](#バルクヘッド): サーキットブレーカーは「止める」、バルクヘッドは「隔離する」
- [レートリミット](#レートリミット): レートリミットは受信側の防御、サーキットブレーカーは送信側の防御
- [グレースフルデグラデーション](#グレースフルデグラデーション): サーキットブレーカーが開いた後にどう振る舞うかの戦略

### 背景・語源
Michael Nygard が2007年の著書 *Release It!* で、電気回路のサーキットブレーカー（遮断器）をソフトウェアパターンに応用して提唱。過負荷時に回路を遮断して機器を保護するように、障害が連鎖する前に呼び出しを遮断するパターン。Netflix の Hystrix（2012年公開）で広く実装・普及した。

### 対策
- Ruby なら `stoplight` gem、Java なら Resilience4j などのライブラリを導入する
- Closed → Open → Half-Open の3状態を意識して閾値とリカバリ時間を設定する
- ブレーカーが開いたときのフォールバック（キャッシュ返却、デフォルト値）を必ず実装する
- CloudWatch Alarm でブレーカーの Open 状態を監視し、通知する

## バックプレッシャー

別名: Back Pressure / 背圧

### 意味
処理能力を超えた流量が来たとき、上流に対して「遅くしてくれ」と伝える仕組み。キューやバッファが溢れる前に、流入量を制御する。

### よくある例
- SQS のキューにメッセージが溜まりすぎたとき、プロデューサー側の送信速度を落とす
- Sidekiq のキューが肥大化しているのにジョブ投入を止めず、メモリが枯渇する（バックプレッシャー不在）
- Kubernetes の HPA がスケールアウトするまでの間、Nginx が 503 を返してクライアントにリトライさせる
- TCP のフロー制御（ウィンドウサイズ）はバックプレッシャーの古典的な例

### ありがちな症状
- キューの深さが単調増加し続けている
- メモリ使用量が時間とともに際限なく増える
- ワーカーの処理速度よりジョブ投入速度のほうが常に速い

### 近い言葉との違い
- [スロットリング](#スロットリング): スロットリングは一律に速度制限する。バックプレッシャーは下流の状態に応じて動的に調整する
- [レートリミット](#レートリミット): 受信側が上限を設けるのがレートリミット。バックプレッシャーは下流から上流への信号
- [サーキットブレーカー](#サーキットブレーカー): バックプレッシャーは「減速」、サーキットブレーカーは「遮断」

### 対策
- キューの深さに閾値を設け、超えたらプロデューサーに通知して投入を抑制する
- SQS + Lambda ならバッチサイズと同時実行数の上限で制御する
- Sidekiq のキューサイズを CloudWatch カスタムメトリクスで監視し、閾値超過でアラート
- ストリーム処理では Reactive Streams のような標準的なバックプレッシャープロトコルを使う

## バルクヘッド

別名: Bulkhead / 隔壁パターン

### 意味
船の隔壁のように、システムのリソースを区画に分離して、ある区画の障害が他に波及しないようにする設計パターン。

### よくある例
- ECS でクリティカルなサービスと非クリティカルなサービスを別クラスターに分離する
- スレッドプールを機能ごとに分け、外部 API 呼び出し用と内部処理用を隔離する
- Sidekiq のキューを `critical`、`default`、`low` に分離し、低優先度のジョブ詰まりが決済処理に影響しないようにする
- RDS のリードレプリカを分析用と本番用で分け、重いクエリが本番に影響しないようにする

### ありがちな症状
- 重要度の低い機能の障害が、決済やログインなど重要機能を巻き込む
- 全サービスが同じデータベース接続プールを共有しており、1つの遅いクエリで接続が枯渇する
- 「なぜか関係ないはずの機能が落ちた」が頻発する

### 近い言葉との違い
- [サーキットブレーカー](#サーキットブレーカー): 障害を「止める」のがサーキットブレーカー、「閉じ込める」のがバルクヘッド
- [SPOF](#spof): バルクヘッドは SPOF による影響範囲を限定する手段
- [グレースフルデグラデーション](#グレースフルデグラデーション): バルクヘッドで隔離した上で、壊れた区画の機能を縮退する

### 背景・語源
船舶の隔壁（bulkhead）に由来。船体を複数の区画に分けることで、一箇所に浸水しても船全体が沈没しないようにする設計。Michael Nygard の *Release It!* でソフトウェアパターンとして紹介され、リソースを分離して障害の影響範囲を限定する手法を指す。タイタニック号の沈没（1912年）は、隔壁が上部で開放されていたために複数区画に浸水が広がった事例として有名。

### 対策
- マイクロサービスごとに独立した DB 接続プール、スレッドプール、キューを持たせる
- ECS / Kubernetes で重要度に応じた Namespace やクラスター分離を行う
- Terraform でリソースグループを分け、blast radius を意識した構成にする
- 接続プールのサイズ上限を明示的に設定し、共有プールの枯渇を防ぐ

## リトライストーム

別名: Retry Storm / リトライの嵐

### 意味
障害が発生したサービスに対して、多数のクライアントが一斉にリトライを繰り返すことで、障害をさらに悪化させる現象。復旧しかけたサービスを再び押しつぶす。

### よくある例
- 外部 API が 503 を返しているのに、全 ECS タスクが即時リトライし、API が復旧できない
- Sidekiq のリトライが指数バックオフなしで設定されており、障害復旧直後に大量のジョブが殺到する
- フロントエンドの fetch が失敗時に即座にリトライし、ALB のリクエスト数が障害前の10倍になる

### ありがちな症状
- 障害が「回復→再発→回復→再発」を繰り返すフラッピング状態になる
- 復旧後にトラフィックが急増し、正常時より負荷が高い
- リトライ起因のリクエスト数がオリジナルの数倍に膨れ上がっている

### 近い言葉との違い
- [サーキットブレーカー](#サーキットブレーカー): リトライストームの根本対策。一定回数失敗したらリトライ自体を止める
- [バックプレッシャー](#バックプレッシャー): 上流に減速を伝える仕組み。リトライストームはバックプレッシャーが機能していない状態
- [レートリミット](#レートリミット): 受信側でリトライストームの流量を制限する手段
- [Thundering Herd](concurrency.md#thundering-herdサンダリングハード): リトライストームと似た集中アクセスだが、キャッシュ失効時などに発生する

### 対策
- リトライには必ず Exponential Backoff + Jitter（ランダムな揺らぎ）を入れる
- リトライ回数に上限を設け、上限を超えたら DLQ（Dead Letter Queue）に送る
- サーキットブレーカーを導入し、障害検知後はリトライ自体を止める
- クライアント側で `Retry-After` ヘッダーを尊重する

## グレースフルデグラデーション

別名: Graceful Degradation / 優雅な劣化

### 意味
システムの一部が故障しても、全体を停止させず、機能を縮小しながらサービスを継続する設計思想。100% か 0% かではなく、70% でも動き続けることを目指す。

### よくある例
- レコメンドエンジンが落ちたとき、パーソナライズされた推薦の代わりに人気ランキングを表示する
- Redis のキャッシュが死んだとき、DB 直接参照にフォールバックして応答速度は落ちるがサービスは継続する
- 外部の決済 API がダウンしたとき、注文を受け付けてキューに入れ、復旧後に処理する

### ありがちな症状
- 依存サービスが1つ落ちただけでアプリ全体が 500 エラーを返す
- 「あの API が動かないと何もできない」という全か無かの設計になっている
- 障害時の振る舞いが定義されていない

### 近い言葉との違い
- [サーキットブレーカー](#サーキットブレーカー): 障害を検知して遮断するのがサーキットブレーカー、遮断後にどう振る舞うかがグレースフルデグラデーション
- [SPOF](#spof): SPOF があるとグレースフルデグラデーションが成立しない
- [バルクヘッド](#バルクヘッド): 障害を隔離するのがバルクヘッド、隔離した上で縮退運転するのがグレースフルデグラデーション

### 対策
- 各機能について「この依存が死んだら何を返すか」をあらかじめ決めておく
- サーキットブレーカーのフォールバック先としてキャッシュやデフォルト値を用意する
- 障害時の振る舞いをテストに含める（Chaos Engineering との組み合わせ）
- 機能フラグ（Feature Flag）で特定機能を動的にオフにできるようにしておく

## レートリミット

別名: Rate Limit / 速度制限

### 意味
一定時間内に受け付けるリクエスト数に上限を設ける仕組み。サービスの過負荷を防ぎ、公平なリソース配分を実現する。

### よくある例
- API Gateway で 1ユーザーあたり 1000 req/min の制限をかける
- Nginx の `limit_req_zone` で IP あたりのリクエスト数を制限する
- Rails の `rack-attack` gem で、ログイン試行を 5回/分 に制限してブルートフォースを防ぐ
- GitHub API の 5000 req/hour のレートリミットに引っかかって CI が失敗する

### ありがちな症状
- 特定ユーザーの大量リクエストが他のユーザーの応答を遅くする
- API に制限がなく、クローラーやボットが全リソースを食い尽くす
- 429 Too Many Requests を返していない（制限がそもそも無い）

### 近い言葉との違い
- [スロットリング](#スロットリング): レートリミットは「拒否」、スロットリングは「遅延させる」ニュアンスが強い
- [バックプレッシャー](#バックプレッシャー): レートリミットは受信側が一方的に制限する。バックプレッシャーは双方向の調整
- [サーキットブレーカー](#サーキットブレーカー): レートリミットは受信側、サーキットブレーカーは送信側の防御

### 対策
- API Gateway や ALB レベルでレートリミットを設定する
- アプリケーション層では `rack-attack`（Rails）や Express の `express-rate-limit` を使う
- 429 レスポンスに `Retry-After` ヘッダーを含めてクライアントに待ち時間を伝える
- Token Bucket や Sliding Window など、用途に合ったアルゴリズムを選ぶ

- [バックプレッシャー](#バックプレッシャー)
- [リトライストーム](#リトライストーム)

## スロットリング

別名: Throttling

### 意味
リクエストやジョブの処理速度を意図的に遅くして、システムが許容できるペースに抑える仕組み。レートリミットが「拒否」なのに対し、スロットリングは「待たせる」。

### よくある例
- AWS API の呼び出しが Throttling エラー（`ThrottlingException`）を返し、Terraform の apply が途中で止まる
- SQS + Lambda の同時実行数を `ReservedConcurrentExecutions` で絞り、下流の DB に過負荷をかけない
- Sidekiq で `concurrency: 5` に設定し、外部 API の同時呼び出し数を制限する
- CloudFront のオリジンリクエスト制限でバックエンドへの流量を制御する

### ありがちな症状
- AWS CLI や SDK で `Rate exceeded` や `Throttling` エラーが頻発する
- バッチ処理が外部 API のレートリミットに引っかかって完了しない
- 同時実行数に制限がなく、DB の接続数上限に達する

### 近い言葉との違い
- [レートリミット](#レートリミット): レートリミットは「超えたら拒否」、スロットリングは「超えたら待たせる」。実際には混用されることが多い
- [バックプレッシャー](#バックプレッシャー): スロットリングは一律制限、バックプレッシャーは下流状態に応じた動的制限
- [サーキットブレーカー](#サーキットブレーカー): スロットリングは「減速」、サーキットブレーカーは「停止」

### 対策
- AWS SDK のリトライ設定で Exponential Backoff を有効にする
- Terraform では `parallelism` オプションで並列実行数を下げる
- Lambda の `ReservedConcurrentExecutions` やバッチサイズで流量を調整する
- バッチ処理では処理間にスリープを入れるか、トークンバケット方式で流量を制御する

## ヘルスチェック

別名: Health Check / 死活監視

### 意味
サービスやコンテナが正常に動作しているかを定期的に確認する仕組み。異常を検知したらトラフィックを切り離したり、再起動したりする。

### よくある例
- ALB のターゲットグループが `/health` エンドポイントに HTTP リクエストを送り、200 以外なら unhealthy としてトラフィックを外す
- ECS タスク定義の `healthCheck` で Docker コンテナのヘルスチェックコマンドを定義する
- Kubernetes の `livenessProbe` と `readinessProbe` でポッドの状態を監視する
- systemd の `ExecStartPost` + `WatchdogSec` でデーモンの死活を監視する

### ありがちな症状
- ヘルスチェックが常に 200 を返すダミー実装で、実際にはDBに繋がっていなくても healthy 扱い
- ヘルスチェックの間隔が長すぎて、障害検知まで数分かかる
- ヘルスチェックが重い処理を実行しており、ヘルスチェック自体がサービスに負荷をかけている

### 近い言葉との違い
- [リードネス](#リードネス): トラフィックを受けられる状態かの確認
- [ライブネス](#ライブネス): プロセスが生きているかの確認
- [Observability](#observabilityオブザーバビリティ): ヘルスチェックは最も基本的な監視手段。Observability はより広い概念

### 対策
- ヘルスチェックエンドポイントでは DB 接続、Redis 接続など主要な依存関係を実際に確認する
- ただし重い処理は避け、軽量かつ高速に応答する設計にする
- `/health`（ライブネス用、軽量）と `/ready`（リードネス用、依存確認あり）を分ける
- ヘルスチェックの失敗閾値・間隔・タイムアウトを適切に設定する（ALB なら interval=30s, threshold=3 など）

## リードネス

別名: Readiness / 準備完了

### 意味
サービスがトラフィックを受け入れる準備ができている状態、またはその確認。ライブネスとは異なり、「生きているが、まだ準備ができていない」状態を区別する。

### よくある例
- Kubernetes の `readinessProbe` が成功するまで、Service のエンドポイントに追加されずトラフィックが来ない
- Rails アプリの起動直後、DB マイグレーションやキャッシュのウォームアップが終わるまで ready ではない
- ECS タスクが起動してから ALB のヘルスチェックに合格するまで、トラフィックがルーティングされない

### ありがちな症状
- デプロイ直後に 500 エラーが一時的に増える（起動途中のインスタンスにリクエストが来ている）
- ローリングアップデート中にエラー率が上がる
- コンテナは起動しているが、依存サービスへの接続がまだ確立していない

### 近い言葉との違い
- [ライブネス](#ライブネス): ライブネスは「生きているか」、リードネスは「受け入れ可能か」
- [ヘルスチェック](#ヘルスチェック): ヘルスチェックはリードネスとライブネスの総称
- [Rolling Update](#rolling-update): リードネスの確認がないローリングアップデートはダウンタイムを生む

### 対策
- Kubernetes では `readinessProbe` を必ず設定し、依存サービスへの接続確認を含める
- ECS では ALB ヘルスチェックの `healthy_threshold` と `interval` を適切に設定する
- アプリケーション側に `/ready` エンドポイントを実装し、DB・Redis・外部 API への接続状態を返す
- `initialDelaySeconds` や `deregistration_delay` を適切に設定してグレースフルな切り替えを実現する

## ライブネス

別名: Liveness / 生存確認

### 意味
プロセスやコンテナが生きていて応答可能かを確認する仕組み。ライブネスが失敗するとプロセスは再起動される。リードネスが「受け入れ準備」なのに対し、ライブネスは「そもそも動いているか」。

### よくある例
- Kubernetes の `livenessProbe` が失敗し、kubelet がポッドを kill して再起動する
- Docker の `HEALTHCHECK` で定期的にプロセスの生存を確認する
- systemd の `WatchdogSec` でプロセスが一定時間応答しなければ再起動する
- Rails アプリがデッドロックに陥り、リクエストに一切応答しなくなっている状態

### ありがちな症状
- プロセスは起動しているが、内部でハングしてリクエストに応答しない
- OOM Killer に殺されかけて極端に遅くなったが、プロセス自体は残っている
- ライブネスチェックが無く、ゾンビ状態のコンテナがロードバランサーの背後にいる

### 近い言葉との違い
- [リードネス](#リードネス): リードネスの失敗はトラフィックを外すだけ。ライブネスの失敗は再起動をトリガーする
- [ヘルスチェック](#ヘルスチェック): ヘルスチェックの一種。ライブネスチェックの結果に応じてコンテナを再起動する
- [Observability](#observabilityオブザーバビリティ): ライブネスは最もプリミティブな監視。Observability はメトリクス・ログ・トレースを含む

### 対策
- Kubernetes ではライブネスとリードネスのプローブを分離して設定する
- ライブネスチェックは軽量にする（DB 接続確認などはリードネスに任せる）
- `failureThreshold` と `periodSeconds` を適切に設定し、一時的なスパイクで再起動ループに入らないようにする
- デッドロック検知には、アプリケーション内部のスレッドダンプや watchdog タイマーも組み合わせる

## Canary Deploy

別名: カナリアデプロイ / カナリアリリース

### 意味
新バージョンをトラフィックの一部（例: 5%）にだけ配信し、問題がないことを確認してから全体に展開するデプロイ手法。炭鉱のカナリアが由来。

### よくある例
- ALB の加重ターゲットグループで新バージョンに 5% のトラフィックを流し、エラー率を監視する
- Kubernetes で Argo Rollouts を使い、段階的にトラフィックを新ポッドにシフトする
- CloudFront + Lambda@Edge でリクエストの一部を新バージョンのオリジンに振り向ける
- ECS のデプロイメント設定で `minimumHealthyPercent` と `maximumPercent` を調整して段階的に展開する

### ありがちな症状
- デプロイ直後に全ユーザーが影響を受け、ロールバックまでの間に大量のエラーが発生する
- 新バージョンの問題を本番トラフィックで検知できる仕組みがない
- デプロイが「出すか出さないか」の二択になっている

### 近い言葉との違い
- [Blue-Green Deployment](#blue-green-deployment): Blue-Green は全トラフィックを一括切り替え。Canary は段階的に切り替え
- [Rolling Update](#rolling-update): Rolling Update はインスタンスを順次入れ替える。Canary はトラフィック比率で制御する
- [グレースフルデグラデーション](#グレースフルデグラデーション): Canary で問題が見つかったときのフォールバック先

### 背景・語源
炭鉱のカナリアに由来。19世紀から20世紀にかけて、炭鉱夫は有毒ガス（一酸化炭素やメタン）の検知のためにカナリアをケージに入れて坑道に持ち込んだ。カナリアが先に影響を受けることで、人間が危険を察知できた。イギリスでは1986年まで実際にこの慣行が続いた。

### 対策
- デプロイパイプラインにカナリアフェーズを組み込み、メトリクス（エラー率、レイテンシ）を自動監視する
- 閾値を超えたら自動ロールバックする仕組みを用意する（Argo Rollouts の `analysis` など）
- カナリアの対象ユーザーを内部ユーザーや特定リージョンに限定してリスクを下げる
- Observability の基盤が整っていないと Canary の効果が半減するので、先にメトリクス・ログ基盤を整える

### 関連用語
- [Blue-Green Deployment](#blue-green-deployment)
- [Rolling Update](#rolling-update)
- [Observability](#observabilityオブザーバビリティ)
- [ヘルスチェック](#ヘルスチェック)
- [カナリアテスト](testing.md#カナリアテスト)

## Blue-Green Deployment

別名: ブルーグリーンデプロイ

### 意味
本番環境を2セット（Blue: 現行、Green: 新版）用意し、切り替えによってデプロイする手法。問題があれば Blue に即座に戻せる。

### よくある例
- Route 53 の加重ルーティングで DNS を切り替えて Blue ↔ Green を入れ替える
- ECS のデプロイメントタイプ `CODE_DEPLOY` で Blue/Green デプロイを行う
- Terraform で ASG を2つ管理し、ALB のターゲットグループを切り替える
- AWS CodeDeploy の Blue/Green デプロイ設定で、Lambda のエイリアスを切り替える

### ありがちな症状
- ロールバックに時間がかかる（環境を1つしか持っていない）
- デプロイ中にダウンタイムが発生する
- 「前のバージョンに戻す」が手作業で手順書頼り

### 近い言葉との違い
- [Canary Deploy](#canary-deploy): Canary はトラフィックを段階的に移行。Blue-Green は一括切り替え
- [Rolling Update](#rolling-update): Rolling Update はインスタンスを順次入れ替え。Blue-Green は環境丸ごと切り替え
- [SPOF](#spof): Blue-Green は切り替え機構自体が SPOF にならないよう注意が必要

### 背景・語源
Martin Fowler と Jez Humble が2010年の著書 *Continuous Delivery* で広めた。2つの同一環境（Blue と Green）を用意し、一方で新バージョンを準備してからトラフィックを切り替えるデプロイ手法。名前の由来は単純に2つの環境を色で区別したもの。

### 対策
- DB スキーマの変更は Blue と Green の両方で動作するよう、後方互換性を保つ
- DNS の TTL を短くしておき、切り替え時の浸透を速める
- 切り替え後に一定時間 Blue 環境を維持し、問題があれば即ロールバック可能にする
- コスト管理のため、切り替え完了後に旧環境を自動で縮退・削除する仕組みを入れる

### 関連用語
- [Canary Deploy](#canary-deploy)
- [Rolling Update](#rolling-update)
- [リードネス](#リードネス)

## Rolling Update

別名: ローリングアップデート / ローリングデプロイ

### 意味
インスタンスやコンテナを一度に全部ではなく、少しずつ順番に新バージョンに入れ替えるデプロイ手法。ダウンタイムなしでデプロイできる。

### よくある例
- Kubernetes の `Deployment` はデフォルトで Rolling Update 戦略を使い、`maxUnavailable` と `maxSurge` で速度を制御する
- ECS サービスの `minimumHealthyPercent: 50`, `maximumPercent: 200` でタスクを段階的に入れ替える
- Ansible の `serial` パラメータでホストを N 台ずつ更新する
- systemd + shell スクリプトで複数サーバーを順次再起動する

### ありがちな症状
- デプロイ中に旧バージョンと新バージョンが同時に稼働し、API の互換性が壊れる
- リードネスチェックが無いため、起動途中のインスタンスにリクエストが来てエラーになる
- デプロイが遅すぎて完了まで30分以上かかる

### 近い言葉との違い
- [Blue-Green Deployment](#blue-green-deployment): 環境丸ごと切り替え。Rolling Update はインスタンス単位で順次入れ替え
- [Canary Deploy](#canary-deploy): Canary はトラフィック比率で制御。Rolling Update はインスタンス数で制御
- [リードネス](#リードネス): Rolling Update が安全に動くにはリードネスチェックが必須

### 対策
- 新旧バージョンが同時に存在することを前提に、API の後方互換性を保つ
- リードネスチェックを必ず設定し、準備完了前にトラフィックが来ないようにする
- `maxUnavailable` を適切に設定して、同時に落ちるインスタンス数を制限する
- DB マイグレーションは Rolling Update と分離し、先に適用しておく（expand-and-contract パターン）

### 関連用語
- [Blue-Green Deployment](#blue-green-deployment)
- [Canary Deploy](#canary-deploy)
- [リードネス](#リードネス)
- [ヘルスチェック](#ヘルスチェック)

## Observability（オブザーバビリティ）

別名: 可観測性

### 意味
システムの内部状態を、外部から出力されるデータ（メトリクス、ログ、トレース）によって理解できる度合い。「監視」が既知の問題を検知するのに対し、Observability は未知の問題を調査できる能力を指す。

### よくある例
- CloudWatch Metrics + Logs + X-Ray の3本柱で ECS サービスの状態を把握する
- Datadog や Grafana でダッシュボードを構築し、レイテンシ・エラー率・スループットを可視化する
- 分散トレーシング（AWS X-Ray、Jaeger）でマイクロサービス間のリクエストフローを追跡する
- 構造化ログ（JSON 形式）で検索・集計を容易にする

### ありがちな症状
- 障害が起きても「何が原因かわからない」状態が長く続く
- ログはあるが非構造化で、grep でしか調査できない
- メトリクスはあるがトレースがなく、どのサービスで遅延しているか特定できない
- アラートが多すぎて本当に重要な異常が埋もれる（アラート疲れ）

### 近い言葉との違い
- [ヘルスチェック](#ヘルスチェック): ヘルスチェックは Observability の最も基本的な部品
- [Toil](#toilトイル): Observability が低いと障害調査が手作業の Toil になる
- [Runbook](#runbook): Observability のデータを使って Runbook の手順を実行する

### 対策
- メトリクス、ログ、トレースの「3つの柱」を整備する
- ログは構造化（JSON）し、リクエスト ID やトレース ID を必ず含める
- RED メソッド（Rate, Errors, Duration）や USE メソッド（Utilization, Saturation, Errors）でメトリクスを設計する
- ダッシュボードは「見るだけ」で終わらず、アラートと連携させて自動通知する

### 関連用語
- [ヘルスチェック](#ヘルスチェック)
- [Toil](#toilトイル)
- [Runbook](#runbook)
- [Chaos Engineering](#chaos-engineering)

## Toil（トイル）

別名: 手作業の運用負荷

### 意味
手作業で、繰り返し発生し、自動化可能で、長期的な価値を生まない運用作業のこと。Google の SRE 本で定義された概念で、「サービスの成長に比例して増える作業」が典型。

### よくある例
- 毎週手動で SSL 証明書を更新する（Let's Encrypt + certbot で自動化すべき）
- デプロイのたびに手動で SSH してサーバーを再起動する（CI/CD で自動化すべき）
- 毎朝ログを目視で確認して異常を探す（アラート設定で自動化すべき）
- 手動で EC2 インスタンスのディスク容量を確認して、溢れそうなら掃除する

### ありがちな症状
- 同じ手順書を週に何度も実行している
- 「これは自分しかできない」と言っている作業が多い
- チームの時間が運用に食われて開発が進まない
- 手順書が存在するが、手順が多すぎて間違いが起きやすい

### 近い言葉との違い
- [Runbook](#runbook): Runbook は Toil を手順化したもの。Toil の次のステップは Runbook の自動化
- [Observability](#observabilityオブザーバビリティ): Observability が低いと障害調査の Toil が増える
- [Chaos Engineering](#chaos-engineering): Chaos Engineering で障害パターンを発見し、対応の Toil を事前に減らす

### 背景・語源
Google の SRE（Site Reliability Engineering）チームが定義・普及させた概念。2016年の書籍 *Site Reliability Engineering*（通称 SRE 本）で体系的に解説された。「プロダクションサービスの運用に関連する手作業で、反復的、自動化可能、戦術的、長期的な価値がなく、サービスの成長に比例して増加する作業」と定義されている。

### 対策
- Toil の量を計測する（週あたり何時間を Toil に費やしているか）
- 自動化の優先順位を「頻度 x 所要時間 x リスク」で決める
- Terraform、Ansible、GitHub Actions などで繰り返し作業を IaC / CI に置き換える
- SRE チームの Toil 比率を 50% 以下に保つことを目標にする（Google SRE のプラクティス）

### 関連用語
- [Runbook](#runbook)
- [Observability](#observabilityオブザーバビリティ)

## Runbook

別名: 運用手順書 / オペレーションマニュアル

### 意味
特定の障害や運用タスクに対して、誰でも同じ手順で対応できるようにまとめたドキュメント。「このアラートが鳴ったら何をするか」を事前に定義しておく。

### よくある例
- 「RDS の CPU が 90% を超えたら」→ スロークエリの確認 → コネクション数の確認 → 必要に応じてリードレプリカ追加
- 「ECS タスクが OOM で再起動を繰り返したら」→ CloudWatch Logs でメモリ使用量を確認 → タスク定義のメモリ上限を引き上げ
- 「デプロイ後にエラー率が上昇したら」→ ロールバック手順 → 原因調査 → 修正後に再デプロイ
- PagerDuty のアラートに Runbook の URL をリンクして、オンコール担当がすぐ参照できるようにする

### ありがちな症状
- 障害時に「誰かに聞かないと対処方法がわからない」
- 同じ障害に対して担当者によって対応がバラバラ
- Runbook があるが古くて現状と合っていない
- 手順が「とりあえず再起動」しか書いていない

### 近い言葉との違い
- [Toil](#toilトイル): Runbook は Toil を手順化したもの。自動化できる Runbook は自動化するべき
- [Observability](#observabilityオブザーバビリティ): Runbook の手順で参照するデータ源が Observability 基盤
- [SPOF](#spof): 人的 SPOF を解消するのが Runbook の重要な役割

### 対策
- 全てのアラートに対応する Runbook を用意する
- Runbook は定期的にレビューし、実際に手順通りに動くか検証する（ゲームデー）
- 自動化可能な Runbook は段階的にスクリプト化・CI 化する
- テンプレートを統一し、「症状」「確認手順」「対処手順」「エスカレーション先」を必ず含める

### 関連用語
- [Toil](#toilトイル)
- [Observability](#observabilityオブザーバビリティ)
- [SPOF](#spof)
- [Chaos Engineering](#chaos-engineering)

## Chaos Engineering

別名: カオスエンジニアリング

### 意味
本番環境やそれに近い環境で意図的に障害を注入し、システムの耐障害性を検証するプラクティス。「壊れたらどうなるか」を障害が起きる前に確認する。

### よくある例
- AWS Fault Injection Simulator（FIS）で EC2 インスタンスを強制停止し、Auto Scaling が正しく動くか確認する
- Netflix の Chaos Monkey がランダムにインスタンスを停止して、冗長性を常にテストする
- 特定の AZ を無効化して、Multi-AZ 構成が本当にフェイルオーバーするか検証する
- ネットワーク遅延を注入して、サーキットブレーカーやタイムアウトの設定値が適切か確認する

### ありがちな症状
- 「Multi-AZ だから大丈夫」と言っているが、実際にフェイルオーバーをテストしたことがない
- 障害時の復旧手順が存在するが、実際に試したことがない
- 「本番で試すなんて危険すぎる」と言ってリスクを先送りしている
- DR（ディザスタリカバリ）計画が机上の空論になっている

### 近い言葉との違い
- [グレースフルデグラデーション](#グレースフルデグラデーション): Chaos Engineering はグレースフルデグラデーションが正しく機能するかを検証する手段
- [Observability](#observabilityオブザーバビリティ): Chaos Engineering の実験結果を評価するには Observability 基盤が必須
- [SPOF](#spof): Chaos Engineering で SPOF を発見する
- [Runbook](#runbook): Chaos Engineering の結果を Runbook にフィードバックする

### 背景・語源
Netflix が2011年に Chaos Monkey を公開したことで始まった。2014年に Netflix の Kolton Andrus と Casey Rosenthal が「Chaos Engineering」という分野を確立。2017年の書籍 *Chaos Engineering: System Resiliency in Practice* で体系化された。「意図的に障害を注入して、システムの耐障害性を本番環境で検証する」というアプローチ。

### 対策
- まずは非本番環境から始め、段階的に本番に拡大する
- 実験の仮説（「AZ-a が落ちてもレイテンシは 2倍以内に収まるはず」）を事前に明文化する
- 爆破半径（blast radius）を制限し、実験が制御不能にならないようにする
- 定期的にゲームデーを実施し、Runbook の手順を実際に試す
- AWS FIS や LitmusChaos などのツールを使い、実験を自動化・再現可能にする

- [グレースフルデグラデーション](#グレースフルデグラデーション)
- [Observability](#observabilityオブザーバビリティ)
- [SPOF](#spof)

## Failover（フェイルオーバー）

別名: フェイルオーバー / 自動切り替え

### 意味
稼働中のシステムやコンポーネントに障害が発生した際、待機系に自動的に切り替える仕組み。

### よくある例
- RDS Multi-AZ のフェイルオーバー
- Route 53 のヘルスチェックベースの DNS フェイルオーバー
- Redis Sentinel によるマスター昇格

### ありがちな症状
- フェイルオーバーに30秒以上かかりユーザーに影響
- フェイルオーバーしたが接続文字列が切り替わらず復旧しない

### 近い言葉との違い
- フェイルセーフ: 安全に停止する設計思想。フェイルオーバーは運用を継続する仕組み
- ロールバック: 障害前の状態に戻す。フェイルオーバーは別システムに切り替える
- 冗長化: フェイルオーバーの前提となるインフラ構成

### 対策
- フェイルオーバーの所要時間を定期的に計測する
- フェイルオーバー後の接続切り替えを自動化する
- [Chaos Engineering](#chaos-engineering) でフェイルオーバーを定期的にテストする

## RTO / RPO

別名: Recovery Time Objective / Recovery Point Objective / 目標復旧時間 / 目標復旧時点

### 意味
RTO は障害発生からサービスが復旧するまでの許容時間。RPO は障害時に失ってよいデータの最大量（時間で表す）。災害復旧計画の基本指標。

### よくある例
- RTO=4時間, RPO=1時間 → 4時間以内に復旧し、最大1時間分のデータ損失を許容
- RDS の自動バックアップ（RPO=5分）
- S3 クロスリージョンレプリケーション（RPO≒リアルタイム）

### ありがちな症状
- DR訓練をしたことがなくRTOが不明
- RPO を意識せずバックアップ間隔を24時間にしている

### 近い言葉との違い
- MTTR: 実際の平均復旧時間。RTO は目標値
- SLO: サービス品質の目標。RTO/RPO はDR固有の目標
- [Failover](#failoverフェイルオーバー): RTO を短縮する手段の一つ

### 背景・語源
事業継続計画（BCP）の分野で確立された指標。ISO 22301（事業継続マネジメントシステム）で標準的に定義。クラウド時代ではマルチAZ/マルチリージョン構成でRTO/RPO を大幅に短縮できるようになった。

### 対策
- BCP の一環として RTO/RPO を明文化する
- DR 訓練を定期的に実施して実測値を把握する
- RPO に基づいてバックアップ頻度を決める

## Error Budget（エラーバジェット）

別名: エラー予算

### 意味
SLO で定義した信頼性目標から逆算した「許容される障害の量」。SLO 99.9% なら月間約43分のダウンタイムがエラーバジェット。

### よくある例
- SLO 99.9% のサービスで今月のエラーバジェットを30%消費済み → リスクの高いデプロイを延期
- エラーバジェットが残っているうちに積極的にリリースする

### ありがちな症状
- SLO だけ定義してエラーバジェットを運用に活かしていない
- エラーバジェットを使い切っても「もう少しなら大丈夫」とリリースを続ける

### 近い言葉との違い
- SLO: 信頼性の目標値。エラーバジェットは SLO から算出される許容量
- SLA: 契約上の保証。SLO は内部目標、エラーバジェットは運用指標
- MTTR: 復旧時間の指標。エラーバジェットは総量の指標

### 背景・語源
Google の SRE チームが提唱。*Site Reliability Engineering*（2016）で体系化。「100% の信頼性は間違った目標である」という前提から、信頼性とリリース速度のトレードオフを定量的に管理する仕組み。

### 対策
- SLO からエラーバジェットを算出しダッシュボードで可視化する
- エラーバジェット枯渇時のポリシーを事前に決める（デプロイ凍結、信頼性改善にリソースを振る等）

## On-call

別名: オンコール / 待機当番

### 意味
本番環境で障害が発生した際に対応するために、勤務時間外でもアラートに応答できる状態を維持する当番制度。

### よくある例
- PagerDuty / OpsGenie でローテーションを組む
- 夜間アラートで起こされて30分以内に対応開始

### ありがちな症状
- 特定の人だけが毎回 On-call になる（属人化）
- アラートが多すぎて On-call 疲れが常態化
- アラートが鳴っても対応手順が不明

### 近い言葉との違い
- ヒーロー運用: 特定の個人に依存する運用。On-call は制度化されたローテーション
- [Runbook](#runbook): On-call 対応者が参照する手順書
- [War Room](#war-room): インシデント対応のエスカレーション先

### 対策
- ローテーションを公平に回す
- On-call 中のアラートは週に2件以下を目標にする（[Toil](#toilトイル) の削減）
- [Runbook](#runbook) を整備して誰でも初期対応できるようにする

## War Room

別名: ウォールーム / インシデント対応室 / Bridge Call

### 意味
重大インシデント発生時に関係者が集まり（物理的またはバーチャルに）、リアルタイムで状況共有・意思決定・対応を行う場。

### よくある例
- 本番DB障害で Slack の専用チャンネルを開設し関係者を招集
- Zoom ブリッジを常時接続して進捗を共有

### ありがちな症状
- インシデント時に「誰に聞けばいいかわからない」状態が続く
- 対応状況が散在して全体像が見えない

### 近い言葉との違い
- ポストモーテム: インシデント後の振り返り。War Room はインシデント中の対応
- [On-call](#on-call): 最初の検知・初期対応。War Room はエスカレーション後の組織的対応
- Bystander Effect: War Room の目的はこれを防ぐこと

### 対策
- インシデントコマンダー（IC）を任命し、指揮系統を明確にする
- 時系列ログを1箇所に集約する
- War Room のテンプレート（参加者・チャンネル・役割分担）を事前に用意する
