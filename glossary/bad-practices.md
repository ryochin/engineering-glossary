# 悪い習慣・バッドプラクティス

---

## バッドノウハウ

別名: Bad Know-how

### 意味
本来不要なはずの回避策・おまじないが、正規の手順として定着してしまった知識のこと。
根本原因を直す代わりに「こうすれば動く」というワークアラウンドが蓄積された状態を指す。

### よくある例
- デプロイ前に「必ず `tmp/cache` を手動で消す」という手順が Runbook に書かれている
- `systemctl restart` の前に `sleep 5` を入れないと起動に失敗する、と口伝されている
- Terraform `apply` が失敗したらまず `state rm` してから再実行する、という暗黙ルールがある

### ありがちな症状
- 手順書に「理由はわからないがこうする」と書かれている
- 新人に説明するとき「おまじないだと思って」と言ってしまう
- 手順を飛ばすと壊れるが、なぜ壊れるか誰も説明できない

### 近い言葉との違い
- [トライバルナレッジ](#トライバルナレッジ) — 文書化されていない知識全般。バッドノウハウはその中でも「本来不要な回避策」に限定される
- [ワークアラウンド](project.md#ワークアラウンド) — 一時的な回避策。バッドノウハウは一時的なはずのものが定着した状態
- [Cargo Cult Programming](#cargo-cult-programming) — 理解せずコードをコピーする行為。バッドノウハウは「手順」に焦点がある

### 対策
- 「なぜこの手順が必要か」を必ずコメントや ADR に残す
- 定期的に手順書を棚卸しし、不要になった手順を削除する
- 根本原因の修正を技術的負債として Issue 化し、優先度をつけて対処する

- [テクニカルデット](#テクニカルデット)

## 呪いのコピペ

別名: Cursed Copy-Paste / コピペプログラミング

### 意味
意味を理解しないまま Stack Overflow や社内コードからコピー&ペーストされたコード片のこと。
動いているように見えるが、前提条件の違いや副作用を考慮していないため、後から予期しない不具合を生む。

### よくある例
- Stack Overflow から CORS 設定をコピーして `Access-Control-Allow-Origin: *` を本番に入れてしまう
- 他チームの Dockerfile をそのまま持ってきたが、`USER root` のまま動かしている
- Rails の migration を別プロジェクトからコピーしたが、インデックス名が重複してエラーになる

### ありがちな症状
- コードに不要なオプションや未使用の変数が残っている
- 同じようなコードブロックが微妙に違う形で複数箇所にある
- 「なぜこの設定があるの?」と聞くと「前からあったから」という回答が返ってくる

### 近い言葉との違い
- [Cargo Cult Programming](#cargo-cult-programming) — より広い概念で、コピペに限らず「理解せず真似る」行為全般
- [バッドノウハウ](#バッドノウハウ) — 手順レベルの話。呪いのコピペはコードレベル
- [Spaghetti Code](#spaghetti-code) — 構造の問題。呪いのコピペは「理解せずに持ってきた」という経緯の問題

### 対策
- コピーしたコードは必ず1行ずつ読み、不要な部分を削除する
- PR レビューで「このコードの出典と意図」を説明できるか確認する
- 共通処理は共有ライブラリやモジュールに切り出して DRY にする

### 関連用語
- [Cargo Cult Programming](#cargo-cult-programming)
- [バッドノウハウ](#バッドノウハウ)
- [テクニカルデット](#テクニカルデット)

## Cargo Cult Programming

別名: カーゴカルトプログラミング

### 意味
なぜ動くのか理解しないまま、既存のコードやパターンを儀式的に真似ること。
「前のプロジェクトでこうしていたから」「サンプルに書いてあったから」で思考停止している状態。

### よくある例
- Kubernetes の `resources.limits` を全 Pod に同じ値でコピーし、実際のリソース使用量を計測していない
- Terraform で `depends_on` を「念のため」全リソースに付けて、apply が遅くなっている
- CI パイプラインに `retry: 3` を全ジョブに付けているが、失敗原因の調査をしていない

### ありがちな症状
- 「なぜこう書いているの?」に対して「チュートリアルに書いてあったから」としか答えられない
- 不要な設定や引数が大量に残っている
- 設定を変えると動かなくなるが、どの設定が本質的に必要か誰も把握していない

### 近い言葉との違い
- [呪いのコピペ](#呪いのコピペ) — コピペが原因の場合に使う。Cargo Cult はコピペに限らず「理解なき模倣」全般
- [バッドノウハウ](#バッドノウハウ) — 手順の蓄積。Cargo Cult は「理解していない」という態度の問題
- [Golden Hammer](anti-patterns.md#golden-hammer) — 1つの手法を何にでも適用すること。Cargo Cult は理解せず真似ること

### 背景・語源
第二次世界大戦中、メラネシアの島民が物資を運んでくる飛行機を再び呼び寄せようと、竹で滑走路や管制塔を模造した「カーゴ・カルト（積荷崇拝）」に由来。Richard Feynman が1974年のカリフォルニア工科大学卒業式スピーチで「Cargo Cult Science（カーゴ・カルト・サイエンス）」として科学的手法の形式だけ真似て本質を理解しない姿勢を批判したことで広まった。プログラミング文脈では、なぜ動くか理解せずにコードをコピーする行為を指す。

### 対策
- コードレビューで「なぜこの実装にしたか」を説明させる
- チュートリアルやサンプルをそのまま使わず、自分の要件に合わせて削ぎ落とす
- 設定値の根拠をコメントや ADR に記録する

- [バッドノウハウ](#バッドノウハウ)
- [Golden Hammer](anti-patterns.md#golden-hammer)

## ショットガンデバッグ

別名: Shotgun Debugging

### 意味
原因を特定せずに、手当たり次第に修正を試みるデバッグ手法。
「とりあえずここを変えてみよう」を繰り返し、偶然直ることを期待する。

### よくある例
- Rails アプリが 500 エラーを返すので、`bundle update` → サーバー再起動 → キャッシュクリア → DB マイグレーションを一気に実行する
- ECS タスクが落ちるので、メモリ・CPU・ヘルスチェック間隔・タイムアウトを同時に変更する
- CI が失敗したので、キャッシュ削除・Ruby バージョン変更・Gem 再インストールを一度にやる

### ありがちな症状
- 1つの PR に無関係な変更が大量に含まれている
- 「何を変えたら直ったかわからないけど直った」という報告がある
- 同じ障害が再発し、前回どう直したか再現できない

### 近い言葉との違い
- [ラバーダックデバッグ](project.md#ラバーダックデバッグ) — 問題を言語化して整理する手法。ショットガンデバッグとは正反対のアプローチ
- [5 Whys](project.md#5-whys) — 根本原因を掘り下げる手法。ショットガンデバッグは根本原因を探さない
- [Shotgun Surgery](#shotgun-surgery) — 1つの変更が多数のファイルに波及する設計上の問題。名前は似ているが別概念

### 対策
- まずログ・メトリクス・エラーメッセージを読み、仮説を立ててから変更する
- 変更は1つずつ行い、効果を確認してから次に進む
- 再現手順を確立してから修正に取りかかる

### 関連用語
- [Shotgun Surgery](#shotgun-surgery)
- [ラバーダックデバッグ](project.md#ラバーダックデバッグ)
- [Heisenbug](testing.md#heisenbug)

## トライバルナレッジ

別名: Tribal Knowledge / 部族的知識

### 意味
特定のチームや個人の頭の中にだけ存在し、文書化されていない知識のこと。
口伝や OJT でしか伝わらないため、人が抜けると失われる。

### よくある例
- 本番 DB のフェイルオーバー手順を知っているのがインフラ担当1人だけ
- 「この cron ジョブは毎月1日に手動で確認が必要」という情報が Slack の過去ログにしかない
- Docker イメージのビルドに特定の環境変数が必要だが、README に書かれていない

### ありがちな症状
- 新メンバーのオンボーディングに異常に時間がかかる
- 担当者が休暇中にインシデントが起きると対応できない
- 「あの人に聞いて」が頻出する

### 近い言葉との違い
- [バッドノウハウ](#バッドノウハウ) — トライバルナレッジの中でも「本来不要な回避策」に限定される
- [属人化](#属人化) — トライバルナレッジが進行した結果、特定の人に依存する状態
- [Bus Factor](#bus-factorバス係数) — トライバルナレッジの深刻度を測る指標

### 対策
- Runbook / Playbook を作成し、手順を文書化する
- ペアオペレーション・モブプログラミングで知識を共有する
- 「自分しか知らないこと」を定期的に洗い出す振り返りを行う

- [Bus Factor](#bus-factorバス係数)
- [バッドノウハウ](#バッドノウハウ)

## 属人化

別名: Key Person Dependency / 属人性

### 意味
特定の業務やシステムの知識・スキルが特定の個人に集中し、その人がいないと業務が回らなくなること。
意図せず発生することが多いが、本人が「自分にしかできない」状況を維持しようとするケースもある。

### よくある例
- Terraform のステートファイル構造を把握しているのが1人だけで、その人が不在だとインフラ変更ができない
- レガシーな Rails アプリの内部構造を知っているのが退職予定のエンジニアだけ
- 本番デプロイの承認・実行権限を持っているのが特定の1人だけ

### ありがちな症状
- 特定の人の PR レビューがボトルネックになっている
- その人の休暇中にリリースが止まる
- 退職の話が出ると「引き継ぎに3ヶ月必要」と言われる

### 近い言葉との違い
- [トライバルナレッジ](#トライバルナレッジ) — 文書化されていない知識。属人化はその結果として起きる状態
- [Bus Factor](#bus-factorバス係数) — 属人化の深刻度を数値化したもの
- [ヒーロー運用](#ヒーロー運用) — 属人化の極端な形。特定の人が毎回障害対応する状態

### 対策
- ローテーション制でオンコール・デプロイ担当を回す
- ドキュメント作成をタスクの完了条件に含める
- コードオーナーを複数人に設定する（CODEOWNERS で2人以上）

### 関連用語
- [トライバルナレッジ](#トライバルナレッジ)
- [ヒーロー運用](#ヒーロー運用)
- [Bus Factor](#bus-factorバス係数)

## ヒーロー運用

別名: Hero Culture / Hero Operation

### 意味
障害やトラブルが発生するたびに特定の「スーパーエンジニア」が駆けつけて解決する運用体制のこと。
短期的には問題が解決するが、その人への依存が深まり、組織としての対応力が育たない。

### よくある例
- 深夜の障害対応がいつも同じ人で、その人の Slack ステータスが常に「オンライン」
- 本番 DB の手動オペレーションを「あの人にしかやらせない」というルールがある
- 特定のエンジニアが休暇を取ると、チーム全体が不安になる

### ありがちな症状
- インシデント対応の担当者が偏っている（ポストモーテムで確認できる）
- 「困ったらXXさんに聞け」がチームの暗黙ルールになっている
- ヒーロー役の人が燃え尽き症候群の兆候を見せている

### 近い言葉との違い
- [属人化](#属人化) — 知識やスキルの偏り全般。ヒーロー運用は特に「障害対応」に焦点がある
- [Bus Factor](#bus-factorバス係数) — ヒーロー運用の状態だと Bus Factor は1になりがち
- [Bystander Effect](project.md#bystander-effect) — ヒーローがいることで他のメンバーが「自分はやらなくていい」と思う現象

### 対策
- オンコールローテーションを導入し、全員が障害対応を経験する
- Runbook を整備して、誰でも対応できるようにする
- ポストモーテムで「なぜ特定の人しか対応できなかったか」を振り返る

### 関連用語
- [属人化](#属人化)
- [Bus Factor](#bus-factorバス係数)
- [Runbook](operations.md#runbook)
- [Blameless Postmortem](project.md#blameless-postmortem)

## Works on my machine

別名: WOMM / 「俺の環境では動く」

### 意味
開発者のローカル環境では動作するが、CI・ステージング・本番など他の環境では動かない状態のこと。
環境差異が原因で発生する、再現性の低いバグの典型的な言い訳。

### よくある例
- macOS で開発しているが、CI は Ubuntu で動いており、パスの大文字小文字の扱いが異なる
- ローカルには古い `.env` が残っていて、必要な環境変数が CI にはセットされていない
- Docker イメージのビルドがローカルキャッシュのおかげで通るが、クリーンビルドだと失敗する

### ありがちな症状
- CI が頻繁に失敗するが、ローカルでは再現できない
- 「手元では通るんだけど...」が PR のコメントに出てくる
- 新メンバーが環境構築に丸1日以上かかる

### 近い言葉との違い
- [フレーキーテスト](testing.md#フレーキーテスト) — テスト自体が不安定。WOMM は環境差異が原因
- [Heisenbug](testing.md#heisenbug) — 観測すると消えるバグ。WOMM は環境依存のバグ
- [Snowflake Server](aws-iac.md#snowflake-server) — サーバーの環境差異。WOMM は開発環境の差異

### 対策
- Docker / devcontainer で開発環境を統一する
- CI と同じ OS・ランタイムバージョンをローカルでも使う
- `.env.example` を用意し、必要な環境変数を明示する
- `make setup` や `bin/setup` のようなワンコマンドセットアップを整備する

### 関連用語
- [フレーキーテスト](testing.md#フレーキーテスト)
- [Snowflake Server](aws-iac.md#snowflake-server)
- [Immutable Infrastructure](aws-iac.md#immutable-infrastructure)

## YOLO Deploy

別名: YOLO デプロイ / Push and Pray

### 意味
テスト・レビュー・ステージング検証などを省略して、いきなり本番環境にデプロイすること。
"You Only Live Once" の略で、「一度きりの人生だし、えいや」と本番に投入する行為。

### よくある例
- 金曜夕方に「軽微な修正だから」と CI をスキップして本番デプロイする
- `terraform apply -auto-approve` を plan 確認なしで本番アカウントに実行する
- hotfix ブランチを PR レビューなしで直接 main にマージしてデプロイする

### ありがちな症状
- 「緊急だから」が免罪符になっている
- デプロイ後に初めて動作確認をしている
- ロールバック手順が整備されていない

### 近い言葉との違い
- [ショットガンデバッグ](#ショットガンデバッグ) — 原因不明のまま修正を試みること。YOLO Deploy は検証を省略して本番投入すること
- [Canary Deploy](operations.md#canary-deploy) — 段階的にリリースする手法。YOLO Deploy とは正反対のアプローチ
- [ClickOps](aws-iac.md#clickops) — GUI で手動操作すること。YOLO Deploy は検証省略の問題

### 対策
- CI/CD パイプラインでテスト・lint を必須ゲートにする
- 本番デプロイには承認フローを設ける（GitHub の環境保護ルールなど）
- 金曜デプロイを禁止、またはデプロイ凍結期間を設定する
- ロールバック手順を事前に用意し、デプロイ後のスモークテストを自動化する

## ブロークンウィンドウ理論

別名: Broken Windows Theory

### 意味
「割れた窓」を放置すると、さらなる荒廃を招くという理論。
ソフトウェア開発では、小さな品質低下（lint 警告の無視、テスト未整備など）を放置すると、チーム全体の品質意識が下がり、問題が加速度的に増えることを指す。

### よくある例
- CI の警告を「既知の問題だから」と無視し続けた結果、新しい警告に誰も気づかなくなる
- `TODO` コメントが数百個あり、新しく書いても誰も対応しない
- テストカバレッジが低いコードに対して「もともとテストないし」と追加を見送る

### ありがちな症状
- lint やコンパイラの警告が大量に出ているが、全員が無視している
- 「前からこうだったから」が変更しない理由になっている
- 新しいコードの品質も徐々に下がっている

### 近い言葉との違い
- [テクニカルデット](#テクニカルデット) — 品質低下の蓄積そのもの。ブロークンウィンドウ理論はその蓄積が加速するメカニズム
- [Lava Flow](anti-patterns.md#lava-flow) — 不要なコードが放置される状態。ブロークンウィンドウの一例
- [Big Ball of Mud](anti-patterns.md#big-ball-of-mud) — 構造が崩壊した状態。ブロークンウィンドウの最終形

### 背景・語源
犯罪学者 James Q. Wilson と George L. Kelling が1982年に *The Atlantic Monthly* 誌で発表した理論。「割れた窓を放置すると、地域全体が荒廃する」という仮説。ソフトウェア開発への応用は *The Pragmatic Programmer*（1999, Andrew Hunt & David Thomas）で広く知られるようになった。小さなコード品質の劣化を放置すると、チーム全体のモラルが下がり、さらなる劣化を招くという比喩。

### 対策
- lint・テスト・型チェックを CI で必須にし、警告を0に保つ（zero warning policy）
- 小さな問題を見つけたら、ボーイスカウトルール（来たときより綺麗にして去る）で対処する
- 技術的負債の解消を定期的にスプリントに組み込む

### 関連用語
- [テクニカルデット](#テクニカルデット)
- [Lava Flow](anti-patterns.md#lava-flow)
- [Big Ball of Mud](anti-patterns.md#big-ball-of-mud)

## テクニカルデット

別名: Technical Debt / 技術的負債

### 意味
短期的な都合（納期、リソース不足）で妥協した設計・実装が、将来の変更コストを増大させること。
金融の「負債」と同様、放置すると「利息」が膨らみ、返済（リファクタリング）コストが増え続ける。

### よくある例
- 「今はハードコードでいいや」と書いた設定値が100箇所に散らばっている
- テストなしで本番投入されたコードが増え、リファクタリングが怖くてできない
- Rails アプリの Fat Model がどんどん肥大化し、1ファイル2000行を超えている

### ありがちな症状
- 新機能の追加に以前の3倍の時間がかかるようになった
- 「触ると壊れるから触らない」というコードがある
- リファクタリングの Issue が溜まり続けて消化されない

### 近い言葉との違い
- [ブロークンウィンドウ理論](#ブロークンウィンドウ理論) — 品質低下が加速するメカニズム。テクニカルデットは蓄積した結果
- [Accidental Complexity](anti-patterns.md#accidental-complexity) — 不要な複雑さ。テクニカルデットの一形態
- [Lava Flow](anti-patterns.md#lava-flow) — 不要なコードの放置。テクニカルデットの一形態

### 背景・語源
Ward Cunningham が1992年の OOPSLA カンファレンスで初めて使った比喩。「最初のコードを出荷することは借金をするようなもので、リファクタリングで返済できる。危険なのは借金を返さないことで、利息（技術的負債の利息）が膨らんでいく」と説明した。Martin Fowler が2003年以降のブログで「Technical Debt Quadrant（技術的負債の四象限）」として体系化した。

### 対策
- 負債を意識的に管理する（Issue 化し、優先度をつける）
- スプリントの一定割合（例: 20%）を負債返済に充てる
- 「意図的な負債」と「無意識の負債」を区別し、意図的なものは ADR に理由を記録する

## マジックナンバー

別名: Magic Number

### 意味
コード中に直接書かれた、意味が不明な数値リテラルのこと。
何を表す数字なのかがコードを読むだけでは判断できず、保守性を著しく下げる。

### よくある例

悪い例:
```ruby
if retries > 3
  raise TooManyRetries
end
sleep(86400)
```

良い例:
```ruby
MAX_RETRIES = 3
if retries > MAX_RETRIES
  raise TooManyRetries
end
sleep(1.day.to_i)
```

- Terraform で `timeout = 300` と書かれているが、単位（秒?ミリ秒?）も根拠も不明
- Kubernetes マニフェストに `replicas: 7` とあるが、なぜ7なのか誰も知らない

### ありがちな症状
- 同じ数値が複数箇所にあり、片方だけ変更されてバグになる
- コードレビューで「この数字は何?」という質問が頻出する
- 設定変更のたびにコードを検索して書き換えている

### 近い言葉との違い
- [マジックストリング](#マジックストリング) — 数値ではなく文字列版の同じ問題
- [Primitive Obsession](#primitive-obsession) — プリミティブ型を多用する設計上の問題。マジックナンバーはその一症状
- [Stringly Typed](#stringly-typed) — 文字列の多用。マジックナンバーは数値の問題

### 対策
- 定数やEnum に名前を付けて定義する
- 設定ファイルや環境変数に外出しする
- lint ルール（例: RuboCop の `MagicNumber`）で検出する

### 関連用語
- [マジックストリング](#マジックストリング)
- [Primitive Obsession](#primitive-obsession)

## マジックストリング

別名: Magic String

### 意味
コード中に直接書かれた、意味が不明な文字列リテラルのこと。
タイポに気づきにくく、リネームの際に grep 頼みになるため保守性が低い。

### よくある例

悪い例:
```ruby
if user.role == "admin"
  # ...
end
if status == "pending_review"
  # ...
end
```

良い例:
```ruby
if user.role == User::ROLE_ADMIN
  # ...
end
if status == Status::PENDING_REVIEW
  # ...
end
```

- Docker Compose で `depends_on` の条件に `service_healthy` とタイポして `service_healty` と書いても、エラーにならず無視される
- Terraform の `instance_type = "t3.micro"` が複数箇所にハードコードされている

### ありがちな症状
- 文字列の一箇所を変えたら、別の箇所でマッチしなくなって不具合が出る
- `grep` で影響範囲を調べないと安全に変更できない
- テストで文字列の一致を検証しており、表記揺れでテストが落ちる

### 近い言葉との違い
- [マジックナンバー](#マジックナンバー) — 数値版の同じ問題
- [Stringly Typed](#stringly-typed) — 型の代わりに文字列を使う設計上の問題。マジックストリングはその一症状
- [Primitive Obsession](#primitive-obsession) — プリミティブ型全般の多用

### 対策
- 定数・Enum・シンボルで置き換える
- 型付き言語なら Enum や Union Type を活用する
- linter で文字列リテラルの直接比較を検出する

### 関連用語
- [マジックナンバー](#マジックナンバー)
- [Stringly Typed](#stringly-typed)
- [Primitive Obsession](#primitive-obsession)

## Shotgun Surgery

別名: ショットガンサージェリー / 散弾銃手術

### 意味
1つの変更要求に対して、多数のファイルやクラスを同時に修正しなければならない設計上の問題。
変更の影響範囲が広すぎて、修正漏れが発生しやすい。

### よくある例
- ユーザーの表示名フォーマットを変更するために、10個以上のコントローラーとビューを修正する必要がある
- ログフォーマットの変更で、全サービスの全ファイルを横断的に修正する
- API のレスポンス形式を変えるために、フロントエンド・バックエンド・テスト・ドキュメントを一斉に書き換える

### ありがちな症状
- 「この変更、何ファイル触るの?」と聞くと10以上の答えが返ってくる
- 修正漏れによるバグが頻発する
- 影響範囲の調査だけで半日かかる

### 近い言葉との違い
- [ショットガンデバッグ](#ショットガンデバッグ) — 手当たり次第にデバッグすること。名前は似ているが全く別概念
- [God Object](#god-object--god-class) — 1つのクラスに責務が集中。Shotgun Surgery は逆に責務が散らばりすぎている
- [Spaghetti Code](#spaghetti-code) — 制御フローの複雑さ。Shotgun Surgery は変更の波及範囲の問題

### 対策
- 関連するロジックを1つのモジュール・クラスに凝集させる（高凝集）
- 変更理由が同じコードは同じ場所に置く（Single Responsibility Principle）
- 横断的関心事（ログ、認証など）は AOP やミドルウェアで一箇所にまとめる

### 関連用語
- [God Object](#god-object--god-class)
- [Spaghetti Code](#spaghetti-code)
- [Separation of Concerns](design.md#separation-of-concerns)

## Stringly Typed

別名: 文字列型依存

### 意味
本来は型や Enum で表現すべきデータを、すべて文字列（String）で扱ってしまう設計のこと。
"Strongly Typed" のもじりで、コンパイル時・実行時のチェックが効かなくなる。

### よくある例

悪い例:
```ruby
def process(action)
  case action
  when "start" then start!
  when "stop"  then stop!
  when "restart" then restart!
  end
end
```

良い例:
```ruby
module Action
  START   = :start
  STOP    = :stop
  RESTART = :restart
  ALL = [START, STOP, RESTART].freeze
end
```

- Terraform の変数に `type = string` を多用し、`"true"` / `"false"` を文字列で受け渡している
- API のステータスを `"1"`, `"2"`, `"3"` という文字列で管理している

### ありがちな症状
- タイポによるバグが多い（`"statr"` と書いても実行時まで気づかない）
- 文字列の比較処理が散在している
- リファクタリング時に影響範囲が特定しにくい

### 近い言葉との違い
- [マジックストリング](#マジックストリング) — 意味不明な文字列リテラル。Stringly Typed は設計パターンとしての問題
- [Primitive Obsession](#primitive-obsession) — プリミティブ型全般の多用。Stringly Typed は特に文字列に限定
- [マジックナンバー](#マジックナンバー) — 数値リテラルの問題。Stringly Typed は文字列の問題

### 対策
- Enum、シンボル、定数、Value Object を導入する
- 型付き言語では Union Type やリテラル型を活用する
- バリデーションを入口で行い、内部では型安全な表現を使う

### 関連用語
- [マジックストリング](#マジックストリング)
- [Primitive Obsession](#primitive-obsession)
- [マジックナンバー](#マジックナンバー)

## Primitive Obsession

別名: プリミティブ型執着

### 意味
ドメインの概念を、専用の型やクラスを作らずに `String`, `Integer`, `Hash` などのプリミティブ型だけで表現してしまう設計上の問題。
バリデーションやロジックが散在し、型による安全性が失われる。

### よくある例

悪い例:
```ruby
def send_email(to, subject, body)
  # to はメールアドレスの文字列
  # でも電話番号を渡してもエラーにならない
end
```

良い例:
```ruby
class EmailAddress
  def initialize(value)
    raise InvalidEmail unless value.match?(EMAIL_REGEX)
    @value = value.freeze
  end
end
```

- 金額を `Integer` で扱い、通貨の概念がないため円とドルを足し算できてしまう
- IP アドレスを文字列で持ち、バリデーションが呼び出し側ごとにバラバラ

### ありがちな症状
- 同じバリデーションロジックが複数箇所に書かれている
- 引数の順番を間違えてもコンパイル・実行時にエラーにならない
- メソッドのシグネチャが `(String, String, String, Integer)` のようになっている

### 近い言葉との違い
- [Stringly Typed](#stringly-typed) — Primitive Obsession の文字列特化版
- [マジックナンバー](#マジックナンバー) — リテラル値の問題。Primitive Obsession は型設計の問題
- [God Object](#god-object--god-class) — 責務の集中。Primitive Obsession は型の不足

### 対策
- Value Object パターンを導入する（`EmailAddress`, `Money`, `UserId` など）
- ファクトリメソッドで生成時にバリデーションを強制する
- 型付き言語ではブランデッド型（Branded Type）やニュータイプパターンを活用する

### 関連用語
- [Stringly Typed](#stringly-typed)
- [マジックナンバー](#マジックナンバー)
- [マジックストリング](#マジックストリング)

## God Object / God Class

別名: 神オブジェクト / 神クラス / Blob

### 意味
あまりにも多くの責務を持ち、あらゆる処理に関与する巨大なクラスやモジュールのこと。
何をするにもこのクラスを触る必要があるため、変更が困難でテストも書きにくい。

### よくある例
- Rails の `User` モデルが認証・認可・通知・課金・プロフィール・管理者機能を全て持っており、3000行を超えている
- `ApplicationHelper` に全ビューのヘルパーメソッドが詰め込まれている
- `Utils` や `Common` という名前のクラスに雑多なメソッドが200個以上ある

### ありがちな症状
- 1ファイルが1000行を超えている
- `git blame` するとほぼ毎日誰かがそのファイルを変更している
- マージコンフリクトが頻発する
- テストファイルも巨大で、実行に時間がかかる

### 近い言葉との違い
- [Spaghetti Code](#spaghetti-code) — 制御フローが複雑に絡み合っている状態。God Object は責務の集中
- [Shotgun Surgery](#shotgun-surgery) — 変更が多数のファイルに波及する問題。God Object は逆に1つに集中しすぎている
- [Big Ball of Mud](anti-patterns.md#big-ball-of-mud) — システム全体の構造が崩壊した状態。God Object はクラスレベルの問題

### 背景・語源
オブジェクト指向設計のアンチパターンとして1990年代から使われている。Arthur Riel の *Object-Oriented Design Heuristics*（1996）で「God Class」として言及。全知全能の神のように、あらゆる責任を一手に引き受けるクラスを皮肉った命名。

### 対策
- Single Responsibility Principle に従い、責務ごとにクラスを分割する
- Rails なら Concern、Service Object、Form Object などで分離する
- 段階的にメソッドを抽出し、委譲パターンで移行する

### 関連用語
- [Spaghetti Code](#spaghetti-code)
- [Shotgun Surgery](#shotgun-surgery)
- [Big Ball of Mud](anti-patterns.md#big-ball-of-mud)
- [Separation of Concerns](design.md#separation-of-concerns)

## Spaghetti Code

別名: スパゲッティコード

### 意味
制御フローが複雑に絡み合い、処理の流れを追うことが困難なコードのこと。
`goto` 文の多用が元々の由来だが、現代では深いネスト、過剰な条件分岐、不明確な依存関係なども含む。

### よくある例
- `if` のネストが5段以上になっている処理
- 1つのメソッドが200行以上あり、複数の責務が混在している
- コールバックの中にコールバックがある（コールバック地獄）
- Rails のコントローラーアクションで、ビジネスロジック・バリデーション・レスポンス構築が一体化している

### ありがちな症状
- コードを読むとき、複数のファイルを行ったり来たりする必要がある
- 「この処理、どこから呼ばれてる?」がすぐに答えられない
- バグ修正で1箇所変えると、予想外の場所が壊れる

### 近い言葉との違い
- [God Object](#god-object--god-class) — 責務の集中。Spaghetti Code は制御フローの複雑さ
- [Big Ball of Mud](anti-patterns.md#big-ball-of-mud) — システム全体の構造崩壊。Spaghetti Code はコードレベルの問題
- [テクニカルデット](#テクニカルデット) — Spaghetti Code は技術的負債の一形態

### 背景・語源
1970年代から使われている最も古典的なコードのアンチパターン表現の一つ。GOTO 文の多用によりフローが絡み合う様をスパゲッティに例えた。Edsger Dijkstra の1968年の論文 *Go To Statement Considered Harmful* が、構造化プログラミングの推進とともにこの問題を顕在化させた。

### 対策
- Early Return パターンでネストを浅くする
- メソッドの抽出で処理を分割する（1メソッド20行以下を目安に）
- 複雑な条件分岐はストラテジーパターンやポリモーフィズムで置き換える
- 循環的複雑度（Cyclomatic Complexity）を lint で計測・制限する

### 関連用語
- [God Object](#god-object--god-class)
- [テクニカルデット](#テクニカルデット)
- [Big Ball of Mud](anti-patterns.md#big-ball-of-mud)
- [Accidental Complexity](anti-patterns.md#accidental-complexity)

## Bus Factor（バス係数）

別名: Truck Factor / Lottery Factor

### 意味
チームの何人が突然離脱（バスに轢かれる、宝くじに当たって退職する等）したらプロジェクトが立ち行かなくなるか、という指標。
Bus Factor が1の場合、その1人が不在になるだけでプロジェクトが止まる。

### よくある例
- インフラ構成を把握しているのが1人だけで、その人が退職したら本番環境の変更ができなくなる
- 特定のマイクロサービスのコードを理解しているのが開発者1人だけ
- CI/CD パイプラインの設定を書いた人が異動し、誰もメンテナンスできない

### ありがちな症状
- `git log --format='%an' | sort | uniq -c | sort -rn` で特定の人のコミットが圧倒的に多い
- コードレビューの Approve が常に同じ人
- 特定領域の質問が常に同じ人に集まる

### 近い言葉との違い
- [属人化](#属人化) — Bus Factor が低い状態を引き起こす原因
- [トライバルナレッジ](#トライバルナレッジ) — Bus Factor を下げる要因の1つ
- [ヒーロー運用](#ヒーロー運用) — Bus Factor = 1 の極端な状態

### 背景・語源
「チームメンバーが何人バスに轢かれたら（= 突然いなくなったら）プロジェクトが破綻するか」という思考実験。正確な初出は不明だが、1990年代のオープンソースコミュニティで広まった。「Truck Factor」や「Lottery Factor（宝くじに当たって辞める人数）」とも呼ばれる。より穏やかな表現として後者が推奨されることもある。

### 対策
- ペアプログラミング・モブプログラミングで知識を分散させる
- CODEOWNERS を複数人に設定する
- ローテーション制でオンコールやコードレビューを回す
- 重要なシステムのドキュメントを必ず書き、定期的にレビューする
- Bus Factor を定期的に可視化し、チームの振り返りで議論する

- [トライバルナレッジ](#トライバルナレッジ)
- [ヒーロー運用](#ヒーロー運用)

## Code Smell（コードスメル）

別名: コードの臭い / 不吉な匂い

### 意味
コードが技術的に間違っているわけではないが、設計上の問題を示唆する兆候。直接的なバグではないが、将来のバグや保守性の低下につながる。

### よくある例
- メソッドが100行を超えている（Long Method）
- 引数が6個以上ある（Long Parameter List）
- 同じ条件分岐が複数箇所にコピーされている

### ありがちな症状
- レビューで「なんか嫌な感じがする」と言われるが具体的な指摘ができない
- リファクタリングの優先度がつけられない

### 近い言葉との違い
- [テクニカルデット](#テクニカルデット) — 技術的負債は広い概念。Code Smell はその具体的なシグナル
- [God Object](#god-object--god-class) — 特定の Code Smell の一種
- [Spaghetti Code](#spaghetti-code) — Code Smell の集合体として現れる状態

### 背景・語源
Martin Fowler が Kent Beck との共著 *Refactoring: Improving the Design of Existing Code*（1999）で体系化。「匂いがするコード」は必ずしもバグではないが、リファクタリングの対象候補として注意すべきサインだと定義。22種類の代表的な Code Smell を分類した。

### 対策
- リンターや静的解析ツール（RuboCop, ESLint, SonarQube）で機械的に検出する
- レビューで Code Smell の名前（Long Method, Feature Envy 等）を共通言語として使う

- [テクニカルデット](#テクニカルデット)
- [God Object](#god-object--god-class)
- [Spaghetti Code](#spaghetti-code)
- [Shotgun Surgery](#shotgun-surgery)

## Dead Code（デッドコード）

別名: 不要コード / 到達不能コード

### 意味
実行されることのないコード、または呼び出し元が存在しない関数・クラス。コードベースに残り続けるとノイズとなり、保守コストを増大させる。

### よくある例
- フィーチャーフラグで無効化されたまま3年放置されたコードパス
- リファクタリングで使われなくなった旧メソッドがそのまま残っている
- `TODO: あとで消す` コメントとともに放置されたコード

### ありがちな症状
- `grep` で参照箇所を探しても呼び出し元が見つからない関数がある
- コードカバレッジで0%の行が大量にある
- 新人が「このコードは何のため？」と質問するが誰も答えられない

### 近い言葉との違い
- [Lava Flow](anti-patterns.md#lava-flow) — Dead Code が蓄積して全体が石化した状態。Dead Code は個別のコード片
- [Code Smell](#code-smellコードスメル) — Dead Code は Code Smell の一種
- [テクニカルデット](#テクニカルデット) — Dead Code はテクニカルデットの構成要素の一つ

### 対策
- CI で未使用コードの検出ツールを回す（Ruby: unused, JS: ts-prune）
- フィーチャーフラグに有効期限を設定し、期限切れのコードは削除する
- 「消すか迷ったら消す。必要になったら git log から復元できる」をチームの原則にする

### 関連用語
- [Lava Flow](anti-patterns.md#lava-flow)
- [Code Smell](#code-smellコードスメル)
- [テクニカルデット](#テクニカルデット)

## Rubber Stamping（形骸化レビュー）

別名: ゴム印レビュー / LGTM マシン / 盲目的承認

### 意味
コードレビューで実質的な確認をせず、形式的に「LGTM（Looks Good To Me）」を押して承認すること。レビュープロセスが品質ゲートとして機能しなくなる。

### よくある例
- 500行の PR に対してレビュー時間が2分で「LGTM」
- チーム内の暗黙の了解で「お互い素通しにしよう」
- レビューが承認数ノルマ化して中身を見ずに approve

### ありがちな症状
- レビュー承認までの平均時間が異常に短い
- レビューコメントがほぼゼロの PR が大半
- レビューを通過したコードに品質問題が頻発する

### 近い言葉との違い
- [Bystander Effect](project.md#bystander-effect) — 「誰かが見ているだろう」でレビューが雑になる
- [属人化](#属人化) — 特定の人のコードだけレビューが甘くなる
- [Cargo Cult Programming](#cargo-cult-programming) — 形式的なプロセスの一例

### 対策
- PR のサイズを200行以下に制限してレビュー負荷を下げる
- レビューチェックリストを用意する
- ペアプログラミングやモブプログラミングをレビューの代替として検討する
- レビューに最低限の時間（例: 100行あたり10分）を目安として設ける

## nit / nitpick

別名: ニット / ニットピック / 些細な指摘

### 意味
コードレビューのコメントに付ける慣習的なプレフィックスで、「ブロッカーではない些細な指摘」を意味する。本来は「些細なことを過剰に粗探しする」というネガティブな英語表現だが、レビュー文化においては逆に「これは必須修正ではないので無視してもよい」という**非ブロッキングを明示するラベル**として定着した。それ自体は悪い習慣ではなく、健全なレビュー文化を支える語彙。

### よくある例
- `nit: 余分なスペースが入っています` — 直してほしいが、マージは止めない
- `nitpick: 変数名を userId より uid にすると揃いそう` — 趣味の範囲、無視可
- GitHub / GitLab の PR コメントで `nit:` `nits:` `nit (non-blocking):` のように先頭に付ける
- Google の Code Review Developer Guide や Chromium のレビュー慣習で公式に紹介されているラベル

### ありがちな症状
- レビューコメントの重要度が区別されておらず、些細な空白指摘がブロッカーと同列に扱われてマージが遅れる
- 逆に `nit:` ばかりが大量に並び、本当に直すべき重大な指摘が埋もれる（"nit洪水"）
- レビュアーが「些細だけど言いたい」を `nit:` でなく無印で書いてしまい、レビュイーがブロッカーと誤解する
- 文化として `nit:` の意味（無視してよい / SHOULD 修正）がチーム内で共有されておらず、人によって解釈がバラバラ

### 近い言葉との違い
- **blocker / blocking**: マージを止める必須指摘。`nit` の対義
- **suggestion**: 改善提案。`nit` より少し重く、検討してほしいニュアンス
- **question**: 質問。指摘ではなく意図確認
- **FYI / praise**: 情報共有や褒め言葉。修正は不要
- [Rubber Stamping](#rubber-stamping形骸化レビュー): nit すら付けず形式承認するアンチパターン。nit は逆に「ちゃんと読んだ証」になる
- **Bike-shedding**: 些細な議論で時間を浪費する現象。`nit:` ラベルは些細な指摘を**軽量化して片付ける**ことで Bike-shedding を防ぐ働きがある

### 背景・語源
英語の `nitpick` は「シラミ（nit）の卵を摘み取る」が原義で、19 世紀から「重箱の隅をつつく」の意で使われてきた。ソフトウェアレビュー文化では 2000 年代後半〜2010 年代に Google や OSS コミュニティで `nit:` プレフィックスの慣習が広まり、Conventional Comments（[conventionalcomments.org](https://conventionalcomments.org/)）という仕様化の動きにもつながった。`nit` のほか `praise`, `question`, `issue`, `suggestion`, `chore` などのラベル体系が提案されている。

### 対策
- チーム内で `nit:` の意味を明文化する（推奨: 「直すかどうかはレビュイー判断、マージはブロックしない」）
- レビューコメントのプレフィックス体系（`nit:` / `suggestion:` / `blocker:` / `question:`）をチームのレビューガイドに記載する
- nit が大量に出る場合は linter / formatter / EditorConfig で機械的に潰し、人間の目を本質的な指摘に集中させる
- レビュイーは nit を全部対応する必要はないが、無視する場合も「次の PR で対応します」など一言返すと感情的な行き違いを防げる
- 重要度が混在しそうなら GitHub の suggestion 機能や [Conventional Comments](https://conventionalcomments.org/) の採用を検討する
