## フールプルーフ

別名: Fool Proof / ポカヨケ

### 意味
ユーザーが誤った操作をしても、システムが危険な状態にならないよう設計する考え方。「人は間違える」を前提とし、間違いを起こせない構造にする。

### よくある例
- Terraform の `prevent_destroy = true` で本番 RDS を誤って削除できないようにする
- AWS の MFA 必須設定で、パスワード漏洩だけではログインできないようにする
- Rails の Strong Parameters で、意図しないカラムが mass assignment されることを防ぐ

### ありがちな症状
- 本番環境に対する破壊的操作に確認ステップがない
- `rm -rf /` のような致命的コマンドが何のガードもなく実行できる
- デプロイスクリプトに環境の検証がなく、本番と検証を間違えて実行できる

### 近い言葉との違い
- [フェイルセーフ](#フェイルセーフ): 故障時に安全側に倒す設計。フールプルーフは人間の誤操作を防ぐ設計
- [イディオットプルーフ](#イディオットプルーフ): ほぼ同義だが、より強い表現。現代ではフールプルーフが好まれる
- [ガードレール](#ガードレール): フールプルーフの実装手段の一つ

### 対策
- 破壊的操作には必ず確認プロンプトや `--force` フラグを要求する
- CI/CD パイプラインで環境名の検証を入れ、誤デプロイを防ぐ
- Terraform の `lifecycle { prevent_destroy = true }` を本番リソースに付与する
- IAM ポリシーで本番リソースへの直接操作を制限する

## フェイルセーフ

別名: Fail Safe

### 意味
システムが故障・異常を検知したとき、安全な状態に移行するよう設計する考え方。「壊れたら止まる」が基本方針。安全 > 可用性。

### よくある例
- ECS タスクがヘルスチェックに失敗したら ALB からターゲットを外し、異常なレスポンスをユーザーに返さない
- CI でテストが 1 件でも失敗したらデプロイをブロックする
- systemd の `Restart=on-failure` でプロセス異常終了時に自動再起動し、中途半端な状態で動き続けない

### ありがちな症状
- エラーが出ているのに処理が続行され、データが壊れる
- 異常検知後もリクエストを受け続け、障害が拡大する
- 「落ちるより動いていた方がマシ」という理由でエラーハンドリングが握り潰されている

### 近い言葉との違い
- [フェイルソフト](#フェイルソフト): 故障時に機能を縮退させつつ動き続ける。フェイルセーフは安全側に停止する
- [フェイルオープン](#フェイルオープン): 故障時にアクセスを許可する。フェイルセーフとは逆方向の判断になることが多い
- [フェイルクローズ](#フェイルクローズ): 故障時にアクセスを遮断する。フェイルセーフの一形態
- [フールプルーフ](#フールプルーフ): 人の誤操作を防ぐ。フェイルセーフはシステム故障時の振る舞い

### 対策
- ヘルスチェックを正しく設定し、異常なインスタンスを自動的に切り離す
- CI/CD にゲートを設け、テスト失敗時はデプロイできないようにする
- 例外を握り潰さず、異常時は明示的にエラーを返すかプロセスを停止する
- サーキットブレーカーパターンで障害の波及を止める

- [フェイルクローズ](#フェイルクローズ)

## フェイルソフト

別名: Fail Soft / グレースフルデグラデーション

### 意味
システムが故障・過負荷のとき、一部の機能を縮退させつつサービス全体は動かし続ける設計。「完全に止める」のではなく「できる範囲で動く」を選ぶ。

### よくある例
- EC サイトでレコメンドエンジンが落ちたとき、レコメンド欄を非表示にして商品一覧と購入機能は維持する
- Redis がダウンしたら、キャッシュなしで直接 DB に問い合わせて応答速度は落ちるが動き続ける
- CDN の PoP が障害を起こしたら、オリジンサーバーへフォールバックする

### ありがちな症状
- 一つのマイクロサービスが落ちるとシステム全体が止まる（フェイルソフトになっていない）
- 依存サービスのタイムアウト設定がなく、障害が連鎖する
- 「全部入り」のモノリスで部分的な縮退ができない

### 近い言葉との違い
- [フェイルセーフ](#フェイルセーフ): 故障時に安全側に停止する。フェイルソフトは縮退して動き続ける
- [フェイルオープン](#フェイルオープン): アクセス制御の文脈で「故障時に許可」。フェイルソフトは機能縮退の文脈
- [サーキットブレーカー](operations.md#サーキットブレーカー): フェイルソフトを実現するための具体的なパターン

### 対策
- マイクロサービス間にサーキットブレーカーを導入し、障害の連鎖を止める
- 依存サービスごとにフォールバック戦略を定義しておく
- フィーチャーフラグで問題のある機能だけを無効化できるようにする
- 非クリティカルな機能は非同期化し、失敗してもメインフローに影響しない設計にする

## フェイルオープン

別名: Fail Open

### 意味
システムが故障・異常のとき、アクセスや処理を「許可」する方向に倒す設計。可用性を優先し、認証・認可の仕組みが壊れてもサービスを止めない選択。セキュリティリスクと引き換えに可用性を取る。

### よくある例
- WAF が障害を起こしたとき、WAF をバイパスしてリクエストをそのままオリジンに通す
- 認証サービスがタイムアウトしたら、一時的に全ユーザーをログイン済みとして扱う（危険な例）
- ファイアウォールが故障したとき、全トラフィックを通過させる

### ありがちな症状
- 認証基盤の障害中に「なぜか全員アクセスできる」と報告される
- セキュリティ装置の障害後にアクセスログに不審な通信が増えている
- 障害復旧後に「あの間は無防備だった」と判明する

### 近い言葉との違い
- [フェイルクローズ](#フェイルクローズ): 故障時にアクセスを遮断する。フェイルオープンとは正反対
- [フェイルセーフ](#フェイルセーフ): 安全側に倒す。セキュリティの文脈ではフェイルクローズがフェイルセーフに近い
- [フェイルソフト](#フェイルソフト): 機能を縮退して動かす。フェイルオープンはアクセス制御を緩める

### 対策
- セキュリティに関わるコンポーネントは原則フェイルクローズにする
- フェイルオープンを選択する場合は、リスクを明文化しステークホルダーの合意を取る
- 障害中のアクセスログを必ず残し、事後監査できるようにする
- フェイルオープン状態の持続時間にタイムアウトを設け、自動的にクローズに戻す

### 関連用語
- [フェイルクローズ](#フェイルクローズ)
- [フェイルセーフ](#フェイルセーフ)
- [ディフェンス・イン・デプス](#ディフェンスインデプス)

## フェイルクローズ

別名: Fail Closed / Fail Secure

### 意味
システムが故障・異常のとき、アクセスや処理を「拒否」する方向に倒す設計。セキュリティを優先し、不明な状態ではすべてをブロックする。可用性と引き換えにセキュリティを取る。

### よくある例
- IAM の認証サービスが応答しないとき、すべての API リクエストを 503 で拒否する
- AWS Security Group はデフォルトで全トラフィックを拒否する（ホワイトリスト方式 = フェイルクローズ）
- Docker コンテナのセキュリティポリシーで、明示的に許可されていない syscall をブロックする（seccomp）

### ありがちな症状
- 認証基盤の障害で全ユーザーがログインできなくなる（意図通りだが影響が大きい）
- ネットワーク障害で内部サービス間通信まで遮断され、復旧が遅れる
- 過度なフェイルクローズで可用性が損なわれ、ビジネスに支障が出る

### 近い言葉との違い
- [フェイルオープン](#フェイルオープン): 故障時にアクセスを許可する。フェイルクローズとは正反対
- [フェイルセーフ](#フェイルセーフ): 安全側に倒す広い概念。セキュリティ文脈ではフェイルクローズがその実装
- [ガードレール](#ガードレール): 予防的な制限の仕組み。フェイルクローズは障害時の振る舞い

### 対策
- セキュリティ関連コンポーネントはフェイルクローズをデフォルトにする
- ただし可用性への影響を評価し、SLO とのバランスを取る
- フェイルクローズが発動した場合の復旧手順を Runbook に明記する
- 冗長化により「フェイルクローズが発動する頻度そのもの」を下げる

## ガードレール

別名: Guardrail

### 意味
開発者や運用者が危険な操作をしたとき、被害を最小限に食い止める仕組みの総称。完全に禁止するのではなく、「落ちても崖の下まではいかない」ようにする。

### よくある例
- AWS Organizations の SCP（Service Control Policy）で、本番アカウントでの EC2 直接起動を禁止する
- Terraform の `prevent_destroy` や `ignore_changes` でリソースの意図しない変更を防ぐ
- CI に `terraform plan` の差分チェックを入れ、削除リソースが N 個以上なら手動承認を要求する
- Kubernetes の ResourceQuota で、1 つの Namespace がクラスタのリソースを食い尽くさないようにする

### ありがちな症状
- 本番環境で誰でも何でもできる状態になっている
- 過去に「手が滑って」本番データを消した事故がある
- `terraform apply` を直接ローカルから実行できる

### 近い言葉との違い
- [フールプルーフ](#フールプルーフ): 誤操作自体を不可能にする。ガードレールは操作は許すが被害を制限する
- [ディフェンス・イン・デプス](#ディフェンスインデプス): 多層防御の概念。ガードレールはその各層の具体的な仕組み
- [フェイルセーフ](#フェイルセーフ): 故障時に安全側に倒す。ガードレールは故障前の予防策

### 対策
- AWS SCP / IAM Boundary でアカウント・ロールレベルの制限を敷く
- CI/CD パイプラインにゲートを設け、本番デプロイは承認必須にする
- Terraform Sentinel や OPA（Open Policy Agent）でポリシーを自動適用する
- 「ガードレールがあるから安心」ではなく、定期的にルールを見直す

## ディフェンス・イン・デプス

別名: Defense in Depth / 多層防御 / 縦深防御

### 意味
単一の防御策に頼らず、複数の層で防御を重ねる設計思想。一つの層が突破されても、次の層で食い止める。「壁は一枚では足りない」という前提に立つ。

### よくある例
- AWS: VPC のネットワーク ACL → Security Group → アプリケーションの認証 → WAF の 4 層で守る
- Web アプリ: 入力バリデーション → パラメータ化クエリ → DB ユーザーの権限最小化 で SQL Injection を多層防御
- CI/CD: lint → ユニットテスト → インテグレーションテスト → ステージング検証 → カナリアデプロイ の各段階でバグを検出

### ありがちな症状
- セキュリティが WAF だけに依存しており、WAF を迂回されると無防備
- 「ファイアウォールがあるから大丈夫」で内部通信がノーガード
- 一つのチェックが失敗したら全部崩れる構成になっている

### 近い言葉との違い
- [ガードレール](#ガードレール): 多層防御の各層を構成する具体的な仕組み
- [フェイルクローズ](#フェイルクローズ): 各層が故障したときの振る舞い方針
- [Single Point of Control](#single-point-of-control): 一箇所で制御する設計。多層防御は多箇所で防ぐ設計

### 背景・語源
軍事戦略に由来する概念。元々は「縦深防御」と訳され、前線が突破されても複数の防衛線で敵の進攻を遅延・阻止する戦略。情報セキュリティでは NSA（米国家安全保障局）が2000年代初頭に提唱し、ファイアウォール・認証・暗号化・監視など複数の防御層を重ねる設計思想として定着した。

### 対策
- ネットワーク・アプリケーション・データの各層で独立した防御を設計する
- 一つの対策が無効化された場合のシナリオをレビューする
- 各層の防御が独立して機能することを確認する（一つの鍵で全部開く設計にしない）
- 定期的にペネトレーションテストで多層防御の有効性を検証する

## サニティチェック

別名: Sanity Check / 正気チェック / スモークテストの簡易版

### 意味
処理の前後で「明らかにおかしい状態」を検出するための簡易的なチェック。厳密なバリデーションではなく、「これが真でなければ何かが根本的に間違っている」という前提条件の確認。

### よくある例
- デプロイ後に `curl` でトップページの HTTP 200 を確認する
- Rails のマイグレーション前に、対象テーブルのレコード数が想定範囲内かチェックする
- Terraform apply 前に、削除されるリソース数が 0 であることを確認する
- バッチ処理の冒頭で入力ファイルのサイズが 0 でないことを確認する

### ありがちな症状
- 空のファイルを読み込んで全件削除バッチが走る
- null や空文字が API 連携の末端まで伝搬してから初めてエラーになる
- 「明らかにおかしい」入力がそのまま処理される

### 近い言葉との違い
- [スモークテスト](testing.md#スモークテスト): デプロイ後にシステム全体が動くか確認する。サニティチェックはより小さく局所的
- バリデーション: 入力値の厳密な検証。サニティチェックは「明らかにおかしい」だけを検出する
- アサーション: コード内の不変条件を宣言的に検証する。サニティチェックは手動・自動問わず広い概念

### 対策
- 重要な処理の入り口でサニティチェックを入れる習慣を付ける
- CI パイプラインにデプロイ後のサニティチェック（HTTP 200 確認等）を組み込む
- バッチ処理では入力データの件数・サイズ・形式を処理前に検証する
- 「何が正常か」を先に定義し、それに合致しなければ早期に fail する

### 関連用語
- [スモークテスト](testing.md#スモークテスト)
- [フールプルーフ](#フールプルーフ)
- [フェイルセーフ](#フェイルセーフ)

## イディオットプルーフ

別名: Idiot Proof

### 意味
フールプルーフとほぼ同義で、「どんなに不注意な操作をしてもシステムが壊れない」設計を指す。ただし「idiot」という表現が攻撃的であるため、現在ではフールプルーフやエラープルーフが好まれる。

### よくある例
- USB コネクタは物理的に逆向きに刺さらない（ハードウェアのイディオットプルーフ）
- AWS の削除保護（Deletion Protection）を有効にして、RDS や ELB を誤って削除できないようにする
- `rm` コマンドのエイリアスに `rm -i` を設定して、削除前に確認を求める

### ありがちな症状
- 新人が本番データベースを DROP できる権限を持っている
- 管理画面に「全件削除」ボタンが確認なしで存在する
- 設定ファイルの typo でサービスがダウンする

### 近い言葉との違い
- [フールプルーフ](#フールプルーフ): 同義。現代ではこちらが推奨される表現
- [ガードレール](#ガードレール): 被害を抑える仕組み。イディオットプルーフは誤操作自体を不可能にする
- [フェイルセーフ](#フェイルセーフ): 故障時の安全設計。イディオットプルーフは人間の操作ミス対策

### 対策
- フールプルーフと同様。用語としてはフールプルーフを使うことを推奨する
- チーム内で「イディオットプルーフ」という表現を使う場合は、人を馬鹿にする意図がないことを明確にする
- 設計レビューでは「この操作を間違えたらどうなるか？」を必ず問う

### 関連用語

- [ガードレール](#ガードレール)

## YAGNI

別名: You Aren't Gonna Need It / ヤグニ

### 意味
「今必要でない機能は作るな」という原則。将来の要件を先読みして実装すると、使われないコードが増え、複雑さだけが残る。実際に必要になったときに作れば十分。

### よくある例
- 悪い例: ユーザーが 100 人なのに、マルチテナント対応やシャーディングを先に作り込む
- 悪い例: 将来の拡張に備えて抽象クラスを 3 層重ねたが、サブクラスは 1 つしかない
- 良い例: まず最もシンプルな実装で動かし、実際にスケールの問題が出てからリファクタリングする

### ありがちな症状
- 「将来こうなるかもしれないから」で作った機能が半年以上使われていない
- 設定項目が大量にあるが、デフォルト値以外で使われているものが 1 割もない
- 抽象化が深すぎて、コードを追うのに何層もジャンプが必要

### 近い言葉との違い
- [Premature Optimization](anti-patterns.md#premature-optimization): 早すぎる最適化。YAGNI はより広く「早すぎる機能追加」全般
- [Gold Plating](anti-patterns.md#gold-plating): 不要な装飾を加える行為。YAGNI は「作らない」判断、Gold Plating は「作りすぎ」の結果
- [Leaky Abstraction](#leaky-abstraction抽象化の漏れ): 抽象化が不完全で内部が漏れる問題。YAGNI は抽象化そのものが不要だった問題

### 背景・語源
Extreme Programming（XP）の原則の一つ。Kent Beck と Ron Jeffries が1990年代後半に提唱。「You Ain't Gonna Need It（それは必要にならない）」の略。実際に必要になるまで機能を実装しないという原則。XP の他の原則（KISS、リファクタリング）と組み合わせて実践する。

### 対策
- 「今のユーザー・データ量・トラフィックで必要か？」を常に問う
- feature flag で将来の拡張ポイントだけ残し、実装は後回しにする
- 設計レビューで「これは YAGNI では？」と問う文化を作る
- 使われていないコードは定期的に削除する

## Leaky Abstraction（抽象化の漏れ）

別名: Leaky Abstraction / 抽象の穴

### 意味
抽象化レイヤーが内部の複雑さを完全に隠蔽できず、利用者が内部実装の詳細を知らなければ正しく使えない状態。Joel Spolsky が提唱した「すべての非自明な抽象化は、多かれ少なかれ漏れている」という法則。

### よくある例
- ORM（ActiveRecord）を使っているのに、N+1 問題を避けるために SQL の知識が必要になる
- Docker でアプリを動かしているのに、ファイルシステムのパーミッションやネットワーク設定で Linux の知識が要求される
- Terraform が CloudFormation の制約を隠蔽しきれず、`depends_on` やリソースの作成順を手動で制御する必要がある

### ありがちな症状
- 「ORM を使っているのに、結局生 SQL を書いている」
- 抽象化レイヤーのバグを回避するために内部実装を調べている
- ドキュメントに「この場合は内部の仕組みを理解する必要があります」と書いてある

### 近い言葉との違い
- [YAGNI](#yagni): 不要な機能を作る問題。Leaky Abstraction は作った抽象化が不完全な問題
- [Accidental Complexity](anti-patterns.md#accidental-complexity): 不要な複雑さ全般。Leaky Abstraction はその一因
- [Separation of Concerns](#separation-of-concerns): 関心の分離。正しく分離できていれば漏れは減る

### 背景・語源
Joel Spolsky が2002年のブログ記事 *The Law of Leaky Abstractions* で提唱した「漏れのある抽象化の法則」。「自明でない抽象化は、ある程度まですべて漏れがある（All non-trivial abstractions, to some degree, are leaky）」という主張。TCP が UDP の上に信頼性を抽象化しているが、パケットロスやレイテンシは隠しきれない例を挙げた。

### 対策
- 抽象化の境界で「利用者が内部を知る必要があるか」を常にレビューする
- 漏れを認識した上で、エスケープハッチ（生 SQL の実行、カスタムリソース等）を明示的に提供する
- 「この抽象化で 80% のケースをカバーし、残り 20% は別の手段を用意する」と割り切る
- 完璧な抽象化は存在しないことを前提に、ドキュメントで制約を明記する

- [YAGNI](#yagni)
- [Abstraction Inversion](anti-patterns.md#abstraction-inversion)

## Separation of Concerns

別名: SoC / 関心の分離

### 意味
ソフトウェアを、それぞれ独立した「関心事」ごとに分割して設計する原則。各モジュールは一つの責務に集中し、他の関心事に依存しないようにする。

### よくある例
- Rails の MVC: Model（データ）、View（表示）、Controller（リクエスト処理）で関心を分離する
- Terraform のモジュール分割: ネットワーク・コンピュート・データベースを別モジュールにする
- Docker Compose: アプリ・DB・Redis・Nginx を別コンテナとし、それぞれ独立してスケール・更新できるようにする

### ありがちな症状
- コントローラーにビジネスロジック・バリデーション・DB アクセス・メール送信が全部入っている
- 一つのファイルを変更すると、無関係に見える機能が壊れる
- Terraform の main.tf が 2000 行を超えている

### 近い言葉との違い
- [Single Point of Control](#single-point-of-control): 一つの関心事を一箇所で管理する。SoC は関心事を分ける原則
- [Leaky Abstraction](#leaky-abstraction抽象化の漏れ): 分離したはずの関心事が漏れ出す状態
- [God Object](bad-practices.md#god-object--god-class): SoC に違反した典型的な結果

### 背景・語源
Edsger Dijkstra が1974年の論文 *On the role of scientific thought* で「関心事の分離」として提唱。「一度に一つの側面に集中し、他の側面は無関係であると信じる技法」と定義した。その後、オブジェクト指向設計、MVC パターン、マイクロサービスなど、ソフトウェア設計の基本原則として広く適用されている。

### 対策
- 一つのクラス・関数・モジュールが複数の責務を持っていないか定期的にレビューする
- 「この変更はどのレイヤーの関心事か？」を自問してからコードを書く
- Terraform は環境・サービス・レイヤーごとにモジュールを分割する
- マイクロサービスへの分割を検討する前に、まずモノリス内での関心の分離を徹底する

## Single Point of Control

別名: 単一制御点

### 意味
ある設定値・ルール・ロジックを一箇所だけで定義し、他の箇所はそこを参照する設計原則。同じ情報が複数箇所にコピーされると、変更漏れや不整合が発生する。DRY 原則の具体的な適用。

### よくある例
- 悪い例: 環境変数のポート番号を Dockerfile、docker-compose.yml、Nginx 設定、アプリ設定の 4 箇所にハードコードする
- 良い例: `.env` ファイルで一元管理し、各設定ファイルから参照する
- 悪い例: Terraform で同じ CIDR ブロックを複数の Security Group に直書きする
- 良い例: `locals` や `variables` で定義し、各リソースから参照する

### ありがちな症状
- 設定値を変更したら一部だけ反映され、環境間で不整合が起きる
- 同じ定数がコードベース内の 5 箇所以上にコピーされている
- 「この値を変えるときはここも変えてください」というコメントがある

### 近い言葉との違い
- [Separation of Concerns](#separation-of-concerns): 関心事を分離する原則。Single Point of Control は一つの関心事を一箇所に集約する原則
- [マジックナンバー](bad-practices.md#マジックナンバー): 名前のない定数。Single Point of Control に違反する典型例
- DRY: 重複を排除する原則の総称。Single Point of Control はその具体的な適用

### 対策
- 定数・設定値は一箇所で定義し、他からは参照のみにする
- Terraform の `variables.tf` / `locals` で値を集約する
- 環境変数は `.env` ファイルや AWS Parameter Store / Secrets Manager で一元管理する
- CI/CD パイプラインの設定値は、リポジトリのルートに置いた設定ファイルから読み取る

## 冪等性（Idempotency）

別名: Idempotence / べき等性

### 意味
同じ操作を何度実行しても結果が変わらない性質。API設計、メッセージキュー、決済処理で特に重要。

### よくある例
- REST API の PUT は冪等だが POST は非冪等。同じ PUT リクエストを何度送っても結果は同じだが、POST は送るたびにリソースが増える
- SQS メッセージの重複配信。At-Least-Once 配信のキューでは、同じメッセージが2回届く前提で処理を設計する必要がある
- 決済 API の二重課金防止。ネットワークエラーでリトライしたとき、同じ決済が2回実行されないようにする

### ありがちな症状
- リトライ時にデータが重複する
- キューのメッセージが2回処理されて不整合が起きる
- 決済が二重に課金される
- API クライアントがタイムアウト後にリトライすると、サーバー側で処理が重複する

### 近い言葉との違い
- アトミック操作: 不可分性の概念であり、冪等性とは別。アトミックでも冪等でない操作（例: カウンターのインクリメント）は存在する
- Idempotency Key: 冪等性を実現するための実装パターン。リクエストごとに一意のキーを付与し、同じキーのリクエストは再処理しない
- [副作用（Side Effect）](#副作用side-effect): 副作用があっても冪等であり得る（例: PUT での上書き）

### 背景・語源
数学用語で f(f(x)) = f(x) を満たす操作を「冪等」と呼ぶ。HTTP 仕様（RFC 7231）では GET / PUT / DELETE を冪等なメソッドと定義している。分散システムの信頼性設計が重要視される中で、ネットワーク障害やメッセージの重複配信への対処として冪等性の概念が再認知された。

### 対策
- Idempotency Key を導入し、リクエストの重複実行を防ぐ
- UPSERT（INSERT ... ON CONFLICT UPDATE）を活用して、重複データの挿入を防ぐ
- 処理前に既存結果を確認し、処理済みならスキップする
- メッセージキューの消費者は「同じメッセージが複数回届く」前提で設計する

## DRY

別名: Don't Repeat Yourself

### 意味
同じ知識やロジックをシステム内で繰り返さない原則。コードだけでなく、設定・ドキュメント・スキーマにも適用される。

### よくある例
- 同じバリデーションロジックがフロントエンドとバックエンドに重複している。片方を修正してもう片方を忘れるとバグになる
- 環境ごとに微妙に違う設定ファイルが散在し、どれが正しいのか分からなくなる
- Terraform で同じ Security Group ルールをコピペして複数リソースに適用している

### ありがちな症状
- 1箇所を直したのに別の場所でまだ古い動作をする
- コピペ修正漏れによるバグが繰り返し発生する
- 「ここも直さないといけない」という暗黙知がコードベースに散在する

### 近い言葉との違い
- [KISS](#kiss): シンプルさ優先の原則。DRY を追求しすぎると抽象化が複雑になり KISS に反する
- [Single Point of Control](#single-point-of-control): DRY の具体的な適用パターン。一つの知識を一箇所で管理する
- WET（Write Everything Twice）: DRY の対義語。あえて重複を許容する考え方。重複が2回までなら抽象化のコストの方が高い場合がある

### 背景・語源
Andrew Hunt と David Thomas の *The Pragmatic Programmer*（1999）で提唱。「すべての知識はシステム内で単一の、曖昧さのない、権威ある表現を持たなければならない」。ただし DRY の過度な適用は「間違った抽象化」を生むため、Sandi Metz の「重複は間違った抽象化より遥かにコストが低い（duplication is far cheaper than the wrong abstraction）」という警句も有名。

### 対策
- コードの重複ではなく「知識の重複」に着目する。見た目が同じでも意味が異なる重複は許容する
- 3回目の重複で初めて抽象化を検討する（Rule of Three）
- 共通ロジックは共有ライブラリやモジュールに切り出し、[Single Point of Control](#single-point-of-control) を維持する

## KISS

別名: Keep It Simple, Stupid / Keep It Short and Simple

### 意味
設計をできるだけシンプルに保つ原則。不必要な複雑さを排除し、理解しやすく保守しやすいシステムを目指す。

### よくある例
- 3行で済む処理に汎用フレームワークを自作する
- 将来使うかもしれないパラメータを先に実装し、設定項目が膨大になる
- Rails の before_action チェーンが10段以上あり、リクエストの流れを追えない

### ありがちな症状
- コードを読むのに元の問題を理解するより時間がかかる
- 「なぜこんなに複雑なのか」と誰もが思うが、壊すのが怖くて誰も触れない
- 新規メンバーのオンボーディングに異常に時間がかかる

### 近い言葉との違い
- [YAGNI](#yagni): 「今不要なものは作らない」という原則。KISS は「作るなら単純に作れ」
- [DRY](#dry): 重複排除の原則。DRY を過度に適用すると抽象化が増え、KISS に反する
- [Accidental Complexity](anti-patterns.md#accidental-complexity): KISS に反した結果として生まれる不要な複雑さ
- [Leaky Abstraction](#leaky-abstraction抽象化の漏れ): KISS に反して作った複雑な抽象化は漏れやすい

### 背景・語源
米海軍の航空機設計者 Kelly Johnson（ロッキード社スカンクワークス）が1960年代に提唱したとされる。「平均的な整備士が戦場で限られた工具だけで修理できなければならない」という設計哲学。ソフトウェアでは Unix 哲学の「一つのことをうまくやる（Do One Thing and Do It Well）」に通じる。

### 対策
- 「これを新人が読んで30分で理解できるか？」をリトマス試験にする
- 抽象化層を増やす前にフラットな実装を試す
- 設計レビューで「もっとシンプルにできないか？」を定型の問いにする
- 読み手の認知負荷を意識し、コードの流れを直線的に保つ

## 結合度と凝集度（Coupling / Cohesion）

別名: Coupling and Cohesion / 疎結合・高凝集

### 意味
結合度はモジュール間の依存の強さ、凝集度はモジュール内の要素の関連性の強さ。良い設計は「疎結合・高凝集」を目指す。

### よくある例
- Rails の Fat Controller: コントローラーにビジネスロジック・バリデーション・メール送信が混在している（低凝集）
- 全サービスが共有DBを直接参照し、テーブルのスキーマ変更が全サービスに波及する（密結合）
- マイクロサービス間でスキーマやデータモデルを共有ライブラリとして配布している（密結合）

### ありがちな症状
- 1つの変更が5つ以上のファイルに波及する（密結合）
- 1つのクラスが無関係な10個の責務を持つ（低凝集）
- あるサービスのデプロイに他サービスとの調整が常に必要になる
- テストで大量のモックが必要になる

### 近い言葉との違い
- [Separation of Concerns](#separation-of-concerns): 関心事を分離する原則。結合度・凝集度はその定量的な尺度
- [God Object](bad-practices.md#god-object--god-class): 低凝集の極端な例。一つのオブジェクトが全責務を持つ
- [Shotgun Surgery](bad-practices.md#shotgun-surgery): 密結合の結果として現れる症状。一つの変更が多数のファイルに散弾銃のように波及する

### 対策
- インターフェースを明示的に定義し、実装の詳細を隠蔽する
- 依存の方向を一方向に統一する（上位モジュールが下位モジュールに依存し、逆はしない）
- マイクロサービス間は API 契約で疎結合にし、共有 DB を避ける
- クラスや関数が「一つの理由でのみ変更される」か確認する（単一責任原則）

## 副作用（Side Effect）

別名: Side Effect

### 意味
関数やメソッドが、戻り値を返す以外に外部の状態を変更すること。DB書き込み、ファイル出力、グローバル変数の変更、メール送信などが該当する。

### よくある例
- getter メソッド内で暗黙にキャッシュを更新する。呼び出し側は「読み取り専用」と思って呼んでいるが、実際は状態が変わっている
- バリデーション関数内でログイン試行回数をインクリメントする。バリデーションの呼び出しがビジネスロジックに影響を与える
- Rails の `before_save` コールバックで外部 API を呼び出す。テスト時に意図しない外部通信が発生する

### ありがちな症状
- テストが実行順序に依存する
- 同じ関数を2回呼ぶと結果が変わる
- モック化が困難で、テストのセットアップが肥大化する
- 「この関数を呼ぶと何が起きるか」がシグネチャからは分からない

### 近い言葉との違い
- [冪等性（Idempotency）](#冪等性idempotency): 副作用があっても冪等であり得る。例えば PUT での上書きは副作用を持つが冪等
- 純粋関数: 副作用のない関数。同じ入力に対して常に同じ出力を返す。テスト容易性が高い
- [Separation of Concerns](#separation-of-concerns): 副作用を適切に分離する設計原則

### 対策
- 副作用を関数の端（エントリーポイント付近）に集約し、コア ロジックは純粋関数にする
- 副作用のある関数とない関数を命名で区別する（Ruby の `!` suffix、`save` vs `validate` など）
- Command Query Separation（CQS）を適用し、状態を変更するメソッドと問い合わせるメソッドを分離する
- テスト時に副作用を差し替えられるよう、依存注入で外部依存を渡す
