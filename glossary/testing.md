# テスト

---

## フレーキーテスト

別名: Flaky Test / 不安定テスト

### 意味
同じコードに対して、実行するたびに成功したり失敗したりするテスト。環境依存・タイミング依存・順序依存などが原因で再現性がない。

### よくある例
- CI で 10 回に 1 回だけ落ちる RSpec のシステムスペック。Capybara の `sleep` や `wait` 不足でタイミングに依存している
- GitHub Actions のマトリクスビルドで特定の OS / Ruby バージョンの組み合わせだけ失敗する
- Docker コンテナ内のテストがポートの競合やネットワーク遅延で不安定になる

### ありがちな症状
- 「もう一回回したら通った」が口癖になっている
- CI の re-run ボタンが磨り減るほど押されている
- テスト失敗を誰も真剣に調べなくなり、本物のバグを見逃す

### 近い言葉との違い
- [Heisenbug](#heisenbug): 観測行為自体が挙動を変えるバグ。フレーキーテストの原因の一つになりうる
- [リグレッションテスト](#リグレッションテスト): 回帰を検出するテスト。フレーキーだと回帰検出の信頼性が崩壊する

### 対策
- テストを決定論的にする。時刻は `travel_to` やクロック注入、ランダム値は固定シードで制御する
- CI でフレーキーテストを自動検出し、隔離キュー（quarantine）に移す
- Capybara 等の E2E では明示的な wait / assertion を使い、`sleep` を避ける
- フレーキー率をメトリクスとして可視化し、閾値を超えたら修正を義務づける

### 関連用語
- [Heisenbug](#heisenbug)
- [E2Eテスト](#e2eテスト)
- [Test Pyramid](#test-pyramid)

## スモークテスト

別名: Smoke Test / ビルド受け入れテスト (BVT)

### 意味
システム全体が「致命的に壊れていないか」を最小限の項目で素早く確認するテスト。深い検証はせず、起動するか・主要画面が開くか程度を見る。

### よくある例
- デプロイ直後に `curl -f https://app.example.com/health` でヘルスチェックエンドポイントを叩く
- ECS サービスのローリングデプロイで新タスクのヘルスチェックが通るか ALB が判定する
- Terraform apply 後に `terraform output` で主要リソースの ARN が取れることを確認する

### ありがちな症状
- デプロイ後に「画面が真っ白」と報告が来てから気づく
- ステージング環境にデプロイしたが、DB マイグレーション漏れで起動すらしていなかった
- 本番リリース直後の障害が多い

### 近い言葉との違い
- [サニティテスト](#サニティテスト): スモークは「壊れてないか」、サニティは「直したところが本当に直ったか」
- [E2Eテスト](#e2eテスト): E2E はユーザーシナリオ全体を通す。スモークは最小限の確認
- [カナリアテスト](#カナリアテスト): カナリアは一部のトラフィックで段階的に検証する手法

### 背景・語源
電子工学に由来。新しい回路基板に初めて通電したとき、煙が出なければ最低限の品質はクリアしている、という慣習から「smoke test」と呼ばれるようになった。ソフトウェア開発では、ビルド後やデプロイ後の最初の基本動作確認テストを指す。

### 対策
- CI/CD パイプラインのデプロイステージ直後にスモークテストを必ず組み込む
- ヘルスチェックエンドポイントには DB 接続・Redis 接続・外部 API 疎通を含める
- 失敗時は自動ロールバックを発動させる（ECS のデプロイサーキットブレーカー等）

- [カナリアテスト](#カナリアテスト)
- [E2Eテスト](#e2eテスト)

## サニティテスト

別名: Sanity Test / 健全性テスト

### 意味
特定のバグ修正や機能変更が意図どおりに動くかを局所的に確認するテスト。スモークテストより焦点が狭く、「この修正で本当に直ったか？」を検証する。

### よくある例
- 「ログインできない」バグを修正した後、ログインフローだけを手動で確認する
- Rails の DB マイグレーションを追加した後、該当モデルの CRUD が動くか確認する
- Nginx の設定変更後に `nginx -t` でシンタックスチェックし、対象パスだけ curl で叩く

### ありがちな症状
- 修正をリリースしたが「直ってない」と言われる（サニティテストを省略した）
- 修正箇所は直ったが、別の箇所が壊れていた（サニティだけでリグレッションテストを省略した）

### 近い言葉との違い
- [スモークテスト](#スモークテスト): スモークはシステム全体の生死確認。サニティは特定の変更に焦点を当てる
- [リグレッションテスト](#リグレッションテスト): リグレッションは広範囲の回帰検証。サニティはピンポイント

### 対策
- PR レビュー時に「この修正のサニティテストは何をした？」を確認する文化をつくる
- サニティテストの手順をチケットやPRに明記する
- サニティで OK を確認した後、リグレッションテストも必ず回す

### 関連用語
- [スモークテスト](#スモークテスト)
- [リグレッションテスト](#リグレッションテスト)

## リグレッションテスト

別名: Regression Test / 回帰テスト

### 意味
既存の機能が新しい変更によって壊れていないかを検証するテスト。「前は動いていたものが動かなくなった」を防ぐためのセーフティネット。

### よくある例
- Rails アプリで新機能ブランチをマージした後、CI で全テストスイートを回す
- Terraform モジュールのリファクタリング後に `terraform plan` で差分が出ないことを確認する
- ライブラリのバージョンアップ後に既存のインテグレーションテストを全件実行する

### ありがちな症状
- 「何も変えてないのに壊れた」（実は依存ライブラリが更新されていた）
- リリースノートに書かれていない挙動変更が本番で発覚する
- テストスイートの実行時間が長すぎてスキップされがち

### 近い言葉との違い
- [サニティテスト](#サニティテスト): サニティは変更箇所のみ。リグレッションは広範囲
- [スナップショットテスト](#スナップショットテスト): スナップショットは出力の差分検出に特化した回帰テストの一形態
- [ゴールデンテスト](#ゴールデンテスト): ゴールデンも期待値ファイルとの比較で回帰を検出する手法

### 対策
- CI で全テストスイートを毎回回す。遅い場合はテストの並列化・分割を検討する
- バグ修正時は必ず再現テストを先に書いてからコードを直す（テストファーストで回帰を防ぐ）
- 依存ライブラリの更新は Dependabot / Renovate で自動化し、CI で回帰を検出する

### 関連用語
- [サニティテスト](#サニティテスト)
- [スナップショットテスト](#スナップショットテスト)
- [ゴールデンテスト](#ゴールデンテスト)

## ゴールデンテスト

別名: Golden Test / Golden Master Test / 特性テスト (Characterization Test)

### 意味
事前に保存した「正解」ファイル（ゴールデンファイル）とプログラムの出力を比較し、差分があれば失敗とするテスト。レガシーコードのリファクタリング時に、挙動を変えていないことを保証するのに有効。

### よくある例
- コンパイラやコード生成ツールの出力を `expected/` ディレクトリに保存し、`diff` で比較する
- Terraform の `plan` 出力を保存しておき、リファクタリング後も同じ plan になることを検証する
- API レスポンスの JSON を固定し、シリアライズの変更を検出する

### ありがちな症状
- ゴールデンファイルが古くなり、意図的な変更なのかバグなのか区別がつかない
- ゴールデンファイルの更新コミットが巨大になり、レビューが困難
- バイナリや環境依存の値（タイムスタンプ等）が混入して常に差分が出る

### 近い言葉との違い
- [スナップショットテスト](#スナップショットテスト): スナップショットはテストフレームワークが自動管理する。ゴールデンは手動管理が多い
- [リグレッションテスト](#リグレッションテスト): ゴールデンテストはリグレッションテストの具体的な実装手法の一つ

### 対策
- ゴールデンファイルの更新は専用コマンド（`UPDATE_GOLDEN=1 rake test` 等）で行い、差分を PR でレビューする
- 環境依存の値（日時・UUID 等）はマスクまたは正規表現マッチで除外する
- ゴールデンファイルが増えすぎたら、スナップショットテストへの移行を検討する

### 関連用語
- [スナップショットテスト](#スナップショットテスト)
- [リグレッションテスト](#リグレッションテスト)

## スナップショットテスト

別名: Snapshot Test

### 意味
テスト実行時の出力をファイルに保存し、次回以降の実行結果と自動比較するテスト。Jest のスナップショット機能が代表例。ゴールデンテストをフレームワークレベルで自動化したもの。

### よくある例
- Jest で React コンポーネントのレンダリング結果を `.snap` ファイルに保存して差分を検出する
- Rails の View のレンダリング結果をスナップショットとして保存する
- CLI ツールのヘルプ出力やエラーメッセージの変更を検知する

### ありがちな症状
- `jest --updateSnapshot` を考えずに実行し、壊れたスナップショットを「正解」として上書きしてしまう
- `.snap` ファイルの差分が大きすぎてレビューで読み飛ばされる
- スナップショットが多すぎてテストの意図が不明瞭になる

### 近い言葉との違い
- [ゴールデンテスト](#ゴールデンテスト): ゴールデンは手動管理が中心。スナップショットはフレームワークが自動管理する
- [リグレッションテスト](#リグレッションテスト): スナップショットテストは回帰検出の一手法
- [ユニットテスト](#ユニットテスト): ユニットテストは振る舞いの正しさを検証。スナップショットは「前と同じか」を検証

### 対策
- スナップショットは小さく保つ。コンポーネント全体ではなく、重要な部分だけをスナップする
- スナップショットの更新は PR で必ず差分をレビューする
- 意図的な変更かどうかをコミットメッセージに明記する

### 関連用語
- [ゴールデンテスト](#ゴールデンテスト)
- [リグレッションテスト](#リグレッションテスト)
- [ユニットテスト](#ユニットテスト)

## E2Eテスト

別名: End-to-End Test / エンドツーエンドテスト

### 意味
ユーザーの操作シナリオを最初から最後まで通して検証するテスト。ブラウザ操作、API 呼び出し、DB 書き込み、外部サービス連携など、システム全体を実際に動かして確認する。

### よくある例
- Playwright / Cypress でブラウザを起動し、ユーザー登録 → ログイン → 商品購入 → メール受信を一気通貫で検証する
- Rails のシステムスペック（Capybara + Selenium）で管理画面の CRUD 操作をテストする
- ECS 上のマイクロサービス群を docker-compose で立ち上げ、API ゲートウェイ経由のシナリオを実行する

### ありがちな症状
- テストの実行時間が 30 分以上かかり、CI のボトルネックになっている
- ブラウザのバージョンアップやChromeDriverの不一致で突然全件失敗する
- 外部サービス（決済API等）の sandbox 環境が不安定でフレーキーになる

### 近い言葉との違い
- [インテグレーションテスト](#インテグレーションテスト): インテグレーションはコンポーネント間の結合を検証。E2E はユーザー視点でシステム全体を検証
- [スモークテスト](#スモークテスト): スモークは「壊れてないか」の最小確認。E2E はシナリオ全体を通す
- [ユニットテスト](#ユニットテスト): ユニットは単一コンポーネント。E2E はシステム全体

### 対策
- E2E テストは本当に重要なシナリオだけに絞る（Test Pyramid の頂点）
- 不安定な外部依存は WireMock / VCR 等でスタブ化を検討する
- テストデータのセットアップは API / Factory 経由で行い、UI 操作で作らない
- CI では並列実行とテスト分割（Knapsack 等）で実行時間を短縮する

### 関連用語
- [フレーキーテスト](#フレーキーテスト)
- [インテグレーションテスト](#インテグレーションテスト)
- [Test Pyramid](#test-pyramid)
- [Test Double（モック / スタブ / フェイク）](#test-doubleモック--スタブ--フェイク)

## ユニットテスト

別名: Unit Test / 単体テスト

### 意味
アプリケーションの最小単位（関数・メソッド・クラス）を外部依存から切り離して検証するテスト。高速に実行でき、バグの箇所を正確に特定できる。

### よくある例
- RSpec で Rails モデルのバリデーションロジックをテストする
- Jest で React のカスタムフックの状態遷移をテストする
- Go の `_test.go` で純粋関数の入出力を検証する

### ありがちな症状
- テストが DB やネットワークに依存しており、ユニットテストのつもりがインテグレーションテストになっている
- モックだらけで実装の詳細に密結合し、リファクタリングするとテストが全部壊れる
- カバレッジは高いのに本番で障害が起きる（結合部分がテストされていない）

### 近い言葉との違い
- [インテグレーションテスト](#インテグレーションテスト): インテグレーションは複数コンポーネントの結合を検証。ユニットは単一コンポーネント
- [E2Eテスト](#e2eテスト): E2E はシステム全体。ユニットは最小単位
- [Test Double（モック / スタブ / フェイク）](#test-doubleモック--スタブ--フェイク): ユニットテストで外部依存を切り離すために使う手法

### 対策
- 外部依存（DB・API・ファイルシステム）はインターフェース経由で注入し、テスト時はTest Doubleに差し替える
- 実装の詳細ではなく振る舞い（入力と出力）をテストする
- Test Pyramid の土台として、最も多くのテストをユニットテストで書く
- カバレッジ数値だけを追わず、境界値・異常系・エッジケースを意識する

### 関連用語
- [インテグレーションテスト](#インテグレーションテスト)
- [Test Double（モック / スタブ / フェイク）](#test-doubleモック--スタブ--フェイク)
- [Test Pyramid](#test-pyramid)

## インテグレーションテスト

別名: Integration Test / 結合テスト

### 意味
複数のコンポーネント（モジュール・サービス・ミドルウェア）を組み合わせた状態で、それらの連携が正しく動くかを検証するテスト。ユニットテストでは見つからない「繋ぎ目」のバグを検出する。

### よくある例
- Rails のリクエストスペックで、コントローラ → サービス → モデル → DB を通して API レスポンスを検証する
- Docker Compose で PostgreSQL と Redis を起動し、Sidekiq ジョブの実行結果をテストする
- AWS の LocalStack を使って S3 アップロード → Lambda 起動 → DynamoDB 書き込みのフローを検証する

### ありがちな症状
- ユニットテストは全部通るのに、結合すると動かない（インターフェースの不一致、型の違い等）
- テスト環境の DB スキーマが本番と乖離していて、テストが通っても本番で失敗する
- テストの前提条件のセットアップが複雑でメンテナンスコストが高い

### 近い言葉との違い
- [ユニットテスト](#ユニットテスト): ユニットは単一コンポーネント。インテグレーションは複数の結合
- [E2Eテスト](#e2eテスト): E2E はユーザー視点で全体を通す。インテグレーションはコンポーネント間の結合に焦点
- [スモークテスト](#スモークテスト): スモークは起動確認。インテグレーションは機能レベルの結合検証

### 対策
- テスト用の外部サービスは Docker Compose / Testcontainers / LocalStack で用意する
- DB のスキーマは CI でマイグレーションを毎回実行して本番と一致させる
- テストデータは Factory パターンで管理し、テスト間の依存をなくす
- 実行時間が長い場合は、変更に関連するテストだけ先に実行し、全件は夜間バッチで回す

### 関連用語
- [ユニットテスト](#ユニットテスト)
- [E2Eテスト](#e2eテスト)
- [Test Pyramid](#test-pyramid)

## Test Double（モック / スタブ / フェイク）

別名: Test Double / テストダブル

### 意味
テスト対象の外部依存を置き換えるオブジェクトの総称。モック・スタブ・フェイク・スパイ・ダミーなど種類がある。Gerard Meszaros が体系化した用語。

**スタブ (Stub)**: 決められた値を返すだけの代替。呼び出し側の振る舞いをテストするために使う。
**モック (Mock)**: 期待される呼び出し（引数・回数）を検証する代替。「正しく呼ばれたか」をテストする。
**フェイク (Fake)**: 簡易的だが実際に動く実装。インメモリ DB やローカルの S3 互換サーバー（MinIO）など。

### よくある例
- RSpec の `allow(service).to receive(:call).and_return(result)` はスタブ
- RSpec の `expect(mailer).to have_received(:deliver_later).once` はモック
- テスト用にインメモリの Redis（fakeredis）を使うのはフェイク
- Jest の `jest.fn()` で関数の呼び出し回数と引数を検証するのはスパイ + モック

### ありがちな症状
- モックだらけでテストが実装の詳細に密結合し、リファクタリングのたびにテストが壊れる
- スタブの戻り値が本番の実際のレスポンスと乖離していて、テストは通るが本番で落ちる
- 「モック」「スタブ」を区別せずに使っていて、テストの意図が不明瞭

### 近い言葉との違い
- スタブ vs モック: スタブは「何を返すか」を制御。モックは「どう呼ばれたか」を検証
- フェイク vs スタブ: フェイクは実際に動作する簡易実装。スタブは固定値を返すだけ
- スパイ: 本物のオブジェクトをラップし、呼び出しを記録する。振る舞いは変えない
- ダミー: 引数を埋めるためだけに渡す。実際には使われない

### 背景・語源
Gerard Meszaros が2007年の著書 *xUnit Test Patterns* で定義した総称。映画のスタントダブル（代役）にちなんだ命名で、本物のオブジェクトの代わりにテストで使う代替オブジェクトの総称。Dummy、Stub、Spy、Mock、Fake の5種に分類した。

### 対策
- まずフェイクで済むか検討する。インメモリ DB やLocalStack は結合テストの信頼性を高める
- モックは「境界」（外部 API、メール送信、課金処理）にだけ使い、内部実装にはモックを挟まない
- スタブの戻り値は VCR / WebMock で実際のレスポンスを記録して使う
- テストの意図に応じて適切な種類を選ぶ。「何を検証したいか」を先に決める

- [フレーキーテスト](#フレーキーテスト)

## カナリアテスト

別名: Canary Test / Canary Release / カナリアリリース

### 意味
新バージョンを一部のトラフィック（またはユーザー）にだけ配信し、問題がないことを確認してから全体に展開するテスト手法。炭鉱のカナリアが由来。

### よくある例
- ECS のデプロイで新タスク定義を 10% のトラフィックに配信し、エラー率を監視してから全展開する
- Kubernetes の Argo Rollouts で段階的にトラフィック比率を上げていく
- CloudFront + Lambda@Edge で特定のリクエストヘッダーを持つユーザーだけ新バージョンに振り分ける

### ありがちな症状
- 全トラフィックに一気にデプロイして大規模障害が発生する
- カナリアで異常を検知する仕組みがなく、結局カナリアの意味がない
- カナリア期間が短すぎて、低頻度のバグを見逃す

### 近い言葉との違い
- [スモークテスト](#スモークテスト): スモークはデプロイ直後の起動確認。カナリアは実トラフィックでの段階的検証
- ブルー/グリーンデプロイ: 旧環境と新環境を丸ごと切り替える。カナリアは段階的に比率を変える
- フィーチャーフラグ: コードレベルで機能を切り替える。カナリアはインフラレベルでトラフィックを制御する

### 背景・語源
炭鉱のカナリアに由来。かつて炭鉱夫は有毒ガスの検知のためにカナリア（小鳥）をケージに入れて坑道に持ち込んだ。カナリアが先に影響を受けることで、人間が危険を察知できた。ソフトウェアでは、少数のユーザーやサーバーに先行してリリースし、問題を早期検知する手法を指す。

### 対策
- カナリアのメトリクス（エラー率・レイテンシ・5xx 率）を自動監視し、閾値超過で自動ロールバックする
- AWS CodeDeploy の `CodeDeployDefault.ECSCanary10Percent5Minutes` 等のデプロイ設定を活用する
- カナリア期間中はログとトレースを重点的に監視する
- カナリア対象のユーザーセグメントを意識する（内部ユーザー → ベータユーザー → 全体）

### 関連用語
- [スモークテスト](#スモークテスト)
- [E2Eテスト](#e2eテスト)
- [Canary Deploy](operations.md#canary-deploy)

## Heisenbug

別名: ハイゼンバグ

### 意味
観測しようとすると消える、または挙動が変わるバグ。ハイゼンベルクの不確定性原理に由来。デバッガをアタッチすると再現しない、ログを追加すると直る、といった厄介なバグ。

### よくある例
- マルチスレッドの Rails アプリで、`puts` デバッグを入れるとタイミングが変わり競合状態が再現しなくなる
- Docker コンテナ内でのみ発生し、ローカルの macOS では再現しない（メモリレイアウトの違い）
- CI のデバッグモードを有効にすると実行が遅くなり、タイムアウト系のバグが消える

### ありがちな症状
- 「デバッグすると再現しない」
- 「本番でだけ起きる」
- 「ログを足したら直った」（タイミングが変わっただけ）
- `sleep` を入れると動く、外すと壊れる

### 近い言葉との違い
- [Mandelbug](#mandelbug): Mandelbug は原因が複雑すぎて特定困難なバグ。Heisenbug は観測行為が挙動を変えるバグ
- [フレーキーテスト](#フレーキーテスト): Heisenbug がテストに現れるとフレーキーテストになる

### 背景・語源
Werner Heisenberg（ヴェルナー・ハイゼンベルク）の不確定性原理に由来。Jim Gray が1986年頃に命名したとされる。観測（デバッグ）しようとすると振る舞いが変わって再現しなくなるバグを、量子力学の観測問題になぞらえた。

### 対策
- `puts` / `print` デバッグではなく、構造化ログやトレーシング（OpenTelemetry 等）で非侵入的に観測する
- 競合状態が疑われる場合は ThreadSanitizer (TSan) や Go の `-race` フラグを使う
- 再現条件を狭める: CPU コア数・メモリ・ネットワーク遅延を制御した環境で再現を試みる
- 「ログを追加したら直った」場合、それはタイミング依存のバグであり、根本原因は未解決と認識する

### 関連用語
- [Mandelbug](#mandelbug)
- [フレーキーテスト](#フレーキーテスト)

## Mandelbug

別名: マンデルバグ

### 意味
原因が非常に複雑で、再現条件が多岐にわたり、特定が困難なバグ。マンデルブロ集合のフラクタル的な複雑さに由来。調べれば調べるほど新たな要因が見つかる。

### よくある例
- 特定のタイムゾーン × 特定のロケール × 特定のブラウザバージョンの組み合わせでのみ発生する表示崩れ
- 月末 × 閏年 × 夏時間切り替え日にだけ発生するバッチ処理の不整合
- Kubernetes の Pod が特定ノード × 特定のカーネルバージョン × 特定のネットワークプラグインの組み合わせでのみ OOMKill される

### ありがちな症状
- 原因調査に何日もかかり、調べるたびに新しい条件が見つかる
- 「再現手順」が10ステップ以上ある
- 修正したと思ったら別の条件で再発する

### 近い言葉との違い
- [Heisenbug](#heisenbug): Heisenbug は観測が挙動を変える。Mandelbug は条件の複合が原因
- [フレーキーテスト](#フレーキーテスト): Mandelbug は特定条件で必ず再現する（条件の特定が困難なだけ）

### 背景・語源
Benoît Mandelbrot のマンデルブロ集合に由来。フラクタルのように、原因が複雑に絡み合い、再現条件の特定が極めて困難なバグを表す。Heisenbug と対になる用語として使われる。

### 対策
- 再現条件を一つずつ変数として切り出し、二分探索的に絞り込む
- テスト環境で環境変数・時刻・ロケール・OS をパラメタライズして網羅的に検証する
- 複雑な条件の組み合わせには [Property-based Testing](#property-based-testing) が有効
- 根本原因が特定できたら、その条件の組み合わせをリグレッションテストとして残す

### 関連用語
- [Heisenbug](#heisenbug)
- [Property-based Testing](#property-based-testing)
- [フレーキーテスト](#フレーキーテスト)

## Property-based Testing

別名: プロパティベーステスト / QuickCheck スタイルテスト

### 意味
具体的な入力値ではなく、入出力が満たすべき「性質（プロパティ）」を定義し、ランダム生成された大量の入力で自動検証するテスト手法。バグが見つかると入力を自動的に最小化（shrink）してくれる。

### よくある例
- Haskell の QuickCheck、Python の Hypothesis、Elixir の StreamData、Ruby の Rantly
- 「JSON をシリアライズしてデシリアライズしたら元に戻る」という性質を任意の入力で検証する
- 「ソート関数の出力は常に昇順である」「要素数は変わらない」という性質を検証する

### ありがちな症状
- 手書きのテストケースでは思いつかないエッジケース（空文字列、巨大数、Unicode サロゲートペア等）を見逃している
- 「このテストケースでは通るが、別の入力だと壊れる」が頻発する
- 境界値テストを手動で書くのが辛い

### 近い言葉との違い
- 例示ベーステスト: 具体的な入力と期待値のペアで検証する従来のテスト。Property-based は性質で検証
- [Mutation Testing](#mutation-testing): Mutation はテストの品質を検証する手法。Property-based はテストの書き方の手法
- ファジング: ファジングは主にクラッシュやセキュリティ脆弱性を発見する。Property-based はロジックの正しさを検証する

### 対策
- まず「逆変換が元に戻る」（round-trip）や「冪等性」のようなシンプルな性質から始める
- 入力のジェネレーターをドメインに合わせてカスタマイズする
- CI で実行するときはシードを固定して再現性を確保し、失敗時にシード値を出力する
- 既存のユニットテストを補完する位置づけで導入する

### 関連用語
- [Mutation Testing](#mutation-testing)
- [ユニットテスト](#ユニットテスト)
- [Mandelbug](#mandelbug)

## Mutation Testing

別名: ミューテーションテスト / 変異テスト

### 意味
ソースコードに意図的な小さな変更（ミュータント）を加え、既存のテストがその変更を検出できるかを検証する手法。テスト自体の品質・信頼性を測定する「テストのテスト」。

### よくある例
- Ruby の mutant gem で `>` を `>=` に変えたり、`true` を `false` に変えたりして、テストが失敗するか確認する
- JavaScript の Stryker でコードのミュータントを自動生成し、テストスイートの検出力を測定する
- 条件分岐の `&&` を `||` に変えてもテストが通ってしまう場合、そのテストは不十分

### ありがちな症状
- カバレッジ 100% なのに本番でバグが出る（テストがコードを実行しているだけで、結果を検証していない）
- `assert(true)` のような無意味なアサーションが含まれている
- テストが実装の変更に対して鈍感すぎる

### 近い言葉との違い
- コードカバレッジ: カバレッジは「テストがコードを実行したか」を測定。Mutation Testing は「テストがバグを検出できるか」を測定
- [Property-based Testing](#property-based-testing): Property-based は入力を変えてテストする。Mutation はコードを変えてテストの品質を検証する
- [リグレッションテスト](#リグレッションテスト): リグレッションは意図しない変更を検出する。Mutation は意図的な変更でテストを試す

### 対策
- CI に Mutation Testing を組み込み、ミュータント検出率（mutation score）を追跡する
- 全コードに適用すると遅いので、重要なビジネスロジックに絞って実行する
- 検出されなかったミュータントをもとに、テストケースを追加する
- カバレッジの補完指標として使い、カバレッジだけに頼らない

### 関連用語
- [Property-based Testing](#property-based-testing)
- [ユニットテスト](#ユニットテスト)
- [リグレッションテスト](#リグレッションテスト)

## Test Pyramid

別名: テストピラミッド / テスト自動化ピラミッド

### 意味
Mike Cohn が提唱した、テストの量と粒度の理想的なバランスを示すモデル。下から「ユニットテスト（多い・高速・安価）」→「インテグレーションテスト（中程度）」→「E2Eテスト（少ない・低速・高コスト）」のピラミッド型にする。

### よくある例
- 悪い例（アイスクリームコーン型）: E2E テストが大量にあり、ユニットテストがほとんどない。CI が遅く、フレーキーテストだらけ
- 良い例: ユニットテスト 70% / インテグレーションテスト 20% / E2E テスト 10% の比率
- Rails アプリで、モデルスペック（ユニット）が最も多く、リクエストスペック（インテグレーション）が次に多く、システムスペック（E2E）は主要シナリオのみ

### ありがちな症状
- CI の実行時間が 1 時間を超えている（E2E が多すぎる）
- テストが不安定で信頼されていない（上位レイヤーのテストが多すぎる）
- バグの箇所がテストから特定できない（ユニットテストが足りない）
- 逆に、ユニットテストだけでインテグレーションテストがなく、結合時に壊れる

### 近い言葉との違い
- テストダイヤモンド / テストトロフィー: Kent C. Dodds が提唱。インテグレーションテストを最も重視する形。フロントエンド向き
- テストアイスクリームコーン: アンチパターン。E2E / 手動テストが多く、ユニットテストが少ない逆ピラミッド

### 背景・語源
Mike Cohn が2009年の著書 *Succeeding with Agile* で提唱。ピラミッドの底辺にユニットテスト（大量・高速）、中層にインテグレーションテスト、頂点に E2E テスト（少量・低速）を配置するモデル。Martin Fowler が2012年のブログでさらに広めた。

### 対策
- 新機能の開発時に「このテストはピラミッドのどの層か？」を意識して書く
- E2E テストは「これが壊れたらリリースを止める」レベルのシナリオに限定する
- CI の実行時間を定期的に計測し、遅くなったら層のバランスを見直す
- ユニットテストで十分検証できることをインテグレーションテストで検証していないか確認する

### 関連用語
- [ユニットテスト](#ユニットテスト)
- [インテグレーションテスト](#インテグレーションテスト)
- [E2Eテスト](#e2eテスト)
- [フレーキーテスト](#フレーキーテスト)

## Happy Path

別名: 正常系 / ゴールデンパス / Normal Flow

### 意味
すべての入力が正しく、例外やエラーが一切発生しない理想的な実行経路。ユーザーが期待通りの操作をし、システムが期待通りに応答するシナリオ。

### よくある例
- ログインフォームに正しいメールアドレスとパスワードを入力し、ダッシュボードに遷移する
- API に正しい JSON を POST し、201 Created が返る
- Terraform plan で差分なし → apply が正常完了する

### ありがちな症状
- テストが Happy Path しかカバーしておらず、本番で想定外の入力が来て障害になる
- PR レビューで「Happy Path はわかったけど、エラー時はどうなる？」と毎回指摘される
- デモでは完璧に動くが、実ユーザーの操作で即座に壊れる

### 近い言葉との違い
- [Sad Path](#sad-path): 予想されるエラーや異常系の経路。Happy Path の対義語
- [Edge Case](#edge-case): 入力値の境界条件。Happy Path でも Sad Path でもない「端」のケース
- [Corner Case](#corner-case): 複数の Edge Case が同時に発生する極端な状況
- [スモークテスト](#スモークテスト): Happy Path の最小限のサブセットを確認するテスト

### 対策
- テスト設計時に Happy Path → Sad Path → Edge Case → Corner Case の順で網羅する
- テストケースの一覧に「正常系 / 異常系 / 境界値」のラベルをつけて偏りを可視化する
- コードレビューで「このコードの Sad Path はどこで処理される？」を確認する習慣をつける

### 関連用語
- [Sad Path](#sad-path)
- [Edge Case](#edge-case)
- [Corner Case](#corner-case)
- [スモークテスト](#スモークテスト)
- [E2Eテスト](#e2eテスト)

## Sad Path

別名: 異常系 / Unhappy Path / Error Path / Negative Path

### 意味
ユーザーの誤操作、不正な入力、外部サービスの障害など、予想されるエラーが発生する実行経路。Happy Path の対義語。

### よくある例
- ログインフォームに間違ったパスワードを入力し、「認証に失敗しました」と表示される
- API に不正な JSON を POST し、400 Bad Request が返る
- 外部決済サービスがタイムアウトし、ユーザーに「しばらく待ってから再試行してください」と表示する
- Terraform apply 中に AWS API がレート制限に達し、リトライ後に成功する

### ありがちな症状
- Sad Path のテストがないため、本番でユーザーに 500 Internal Server Error が表示される
- エラーメッセージが「Something went wrong」だけで、ユーザーが何をすればよいかわからない
- 異常系の処理が `rescue => e; nil` のように握りつぶされている

### 近い言葉との違い
- [Happy Path](#happy-path): 正常系。Sad Path はその対義語
- [Edge Case](#edge-case): 境界値の問題。Sad Path は「明らかなエラー」、Edge Case は「ギリギリの値」
- [グレースフルデグラデーション](operations.md#グレースフルデグラデーション): Sad Path が発生したときにサービスを縮退して継続する運用戦略

### 対策
- すべての外部 I/O（DB、API、ファイル）に対してエラーハンドリングを書く
- ユーザー向けのエラーメッセージは「何が起きたか」「何をすればよいか」の2点を含める
- テストでは正常系と異常系を最低でも同数書くことを目安にする
- Rails なら `rescue_from` でコントローラー全体のエラーハンドリングを統一する

### 関連用語
- [Happy Path](#happy-path)
- [Edge Case](#edge-case)
- [Corner Case](#corner-case)
- [グレースフルデグラデーション](operations.md#グレースフルデグラデーション)

## Edge Case

別名: エッジケース / 境界値 / Boundary Case

### 意味
入力値や条件が境界（最小値、最大値、ゼロ、空、nil など）にあるときに発生する問題、またはそれを検証するテストケース。正常と異常の境目に位置する。

### よくある例
- 入力文字列が空文字 `""` や `nil` のとき、バリデーションが意図通り動くか
- ページネーションで0件、1件、ちょうど1ページ分、1ページ+1件のとき
- 日付が月末（2/28, 2/29, 12/31）、タイムゾーン境界（UTC 00:00）、うるう秒
- AWS Lambda のタイムアウト直前（残り100ms）でDB接続を開始するとどうなるか
- 配列のインデックスが0、最後の要素、範囲外のとき

### ありがちな症状
- 「普段は動くけど月末だけ壊れる」バグが定期的に発生する
- ユーザー数が0のときだけダッシュボードが表示崩れする
- 空のリストや nil が渡されたときに `NoMethodError` が出る

### 近い言葉との違い
- [Happy Path](#happy-path): 典型的な正常入力。Edge Case は「端」の値
- [Sad Path](#sad-path): 明確なエラー入力。Edge Case は「エラーかもしれないしそうでないかもしれない」境界
- [Corner Case](#corner-case): 複数の Edge Case が組み合わさった状況。Edge Case は単一条件
- [Property-based Testing](#property-based-testing): ランダムに大量の入力を生成し、Edge Case を自動発見する手法

### 対策
- テスト設計時に境界値分析（Boundary Value Analysis）を意識する: 最小、最小+1、最大-1、最大、範囲外
- `nil` / 空文字 / 空配列 / 0 / 負数は常にテストケースに含める
- Property-based Testing（QuickCheck 系）で人間が見落とす Edge Case を自動検出する

### 関連用語
- [Happy Path](#happy-path)
- [Sad Path](#sad-path)
- [Corner Case](#corner-case)
- [Property-based Testing](#property-based-testing)

## Corner Case

別名: コーナーケース

### 意味
複数の Edge Case が同時に発生する極端な状況。単一の境界条件ではなく、複数の条件が重なったときに初めて顕在化する問題。

### よくある例
- うるう年の2/29かつタイムゾーンが日付変更線付近のユーザーが、深夜0時にパスワードリセットを実行する
- 同時に2人の管理者が同じレコードを編集し、片方が削除・もう片方が更新を押す
- ECS タスクが起動中（readiness probe 未完了）に ALB のヘルスチェック間隔とデプロイタイムアウトが同時に満了する
- Terraform で `count = 0` かつ `depends_on` 先のリソースが `create_before_destroy` のとき

### ありがちな症状
- 「1年に1回だけ起きる」系のバグが本番で発生し、原因特定に時間がかかる
- 再現手順が「AかつBかつCのときだけ」と複雑で、テストに書きづらい
- 障害報告に「こんな操作する人いないでしょ」というコメントがつく（が実際にいる）

### 近い言葉との違い
- [Edge Case](#edge-case): 単一の境界条件。Corner Case は複数の Edge Case の組合せ
- [Heisenbug](#heisenbug): 観測すると消えるバグ。Corner Case は条件が揃えば再現可能
- [Mandelbug](#mandelbug): 原因が複雑なバグ。Corner Case は条件は特定可能だが発生頻度が低い

### 対策
- テスト設計時に「この条件とこの条件が同時に起きたら？」とペアワイズで考える
- Property-based Testing で複数パラメータの組合せを自動探索する
- 障害のポストモーテムで Corner Case が見つかったら、同種の組合せパターンを洗い出す
- 複雑な状態遷移がある箇所にはステートマシン図を書いて、遷移の組合せを網羅する

## Code Coverage（カバレッジ）

別名: テストカバレッジ / コードカバレッジ

### 意味
テストがソースコードのどの程度を実行しているかの指標。行カバレッジ・分岐カバレッジ・条件カバレッジなど複数の種類がある。

### よくある例
- CI で SimpleCov / Istanbul / JaCoCo を使ってカバレッジレポートを出力、「カバレッジ80%以上」をマージ条件にする

### ありがちな症状
- カバレッジは高いのにバグが出る（アサーションなしのテスト）
- カバレッジ目標達成のために無意味なテストが増殖

### 近い言葉との違い
- [Mutation Testing](#mutation-testing): カバレッジが高くてもテストの品質は測れない。Mutation Testing はテストの検出力を測る
- [Test Pyramid](#test-pyramid): カバレッジは量の指標、ピラミッドは構成の指針

### 背景・語源
1963年に Miller と Maloney が提唱した概念。行カバレッジ（C0）・分岐カバレッジ（C1）・条件カバレッジ（C2）の分類が広く使われる。Martin Fowler は「カバレッジは十分なテストの必要条件だが十分条件ではない」と述べている。

### 対策
- カバレッジ目標は手段であり目的ではないと認識する
- 分岐カバレッジも合わせて見る
- カバレッジが低い箇所を優先的にテストする

## Fixture

別名: テストフィクスチャ / テストデータ

### 意味
テスト実行前に用意する前提条件やテストデータのこと。DB のレコード、ファイル、設定値などを含む。

### よくある例
- Rails の `fixtures/` ディレクトリの YAML ファイル
- RSpec の `let` / `before` でのセットアップ
- Factory Bot でのテストデータ生成

### ありがちな症状
- テスト間でデータが干渉する
- Fixture が巨大化して何をテストしているかわからない
- テスト追加のたびに既存 Fixture が壊れる

### 近い言葉との違い
- Factory: テスト内で動的にデータを生成。Fixture は静的に事前定義
- Seed: 開発環境の初期データ。Fixture はテスト専用
- [Test Double（モック / スタブ / フェイク）](#test-doubleモック--スタブ--フェイク): 外部依存の代替。Fixture はデータの準備

### 対策
- Factory パターン（Factory Bot 等）で必要最小限のデータを各テスト内で生成する
- 共有 Fixture は最小限にし、テスト固有のデータはテスト内で定義する

- [インテグレーションテスト](#インテグレーションテスト)

## Shift Left

別名: シフトレフト / Shift-Left Testing

### 意味
テスト・セキュリティ・品質管理などの活動を開発ライフサイクルの早い段階（左側）に移動させるアプローチ。問題を早期に発見し、修正コストを下げる。

### よくある例
- PR 段階で SAST（静的解析）を実行
- 設計レビュー時にセキュリティ要件を検討
- ローカル開発環境で本番相当のテストを実行

### ありがちな症状
- バグが本番デプロイ後にしか見つからない
- セキュリティレビューがリリース直前にボトルネックになる

### 近い言葉との違い
- [Test Pyramid](#test-pyramid): テストの構成バランス。Shift Left はテストの実施タイミング
- CI/CD: Shift Left を実現する基盤
- DevSecOps: セキュリティの Shift Left

### 背景・語源
Larry Smith が2001年に *Dr. Dobb's Journal* で提唱。開発プロセスを左（計画）→右（運用）のタイムラインで表したとき、テストや検証を「左」に移すことで早期発見・早期修正を目指す。近年は DevSecOps の文脈で「セキュリティの Shift Left」として再注目されている。

### 対策
- pre-commit フックで lint・型チェック・SAST を実行
- CI にセキュリティスキャンを組み込む
- 設計ドキュメントのレビューにテスト観点を含める
